RCA-Agent · 公开实例

用确定性机制约束 LLM 的判断与行动 —— 一个把「测量本身可信」当成第一目标的故障根因分析实验。

本页由存档生成（scripts/make_demo.py），不是截图 —— 而存档与录制也随仓库提交（runs/_eval/）， 所以重跑一次生成器就能把这一页**逐字节复现**出来：不需要 API key，不花一分钱。

一、一句话结论

多 Agent 不仅没有价值增量，而且更差。 在同一个世界里，单 Agent 用 ¥0.0172/次拿到 100.0% 准确率； 三专员 + 交叉质证 + 裁决用 ¥0.0732/次 （4.3×）拿到 95.2%（按当前判据） / 90.5%（存档判定） —— 准确率反而低了 4.8 个百分点（但这个差落在轮间波动 14.3 个百分点之内 ⇒ 只能说「没有优势」，不能说「确实更差」—— 见 #46）。

⚠️ 两个口径都给：存档里的判定是当时那版判据给出的；判据后来修过一次（关键词匹配漏了英文词形：retry 匹配不上 retries，见 harness-log #48），所以同一份存档按今天的判据重算会不一样。baseline 存档 100.0% → 按当前判据 100.0%；multi 存档 90.5% → 按当前判据 95.2%。上面的结论用的是按当前判据的那个数；重算只用同一份存档文本 + 当前判据代码，不花一分钱、可自行复跑。

比这个负结果本身更重要的，是它是被测量出来的： 一路上有七八次得到过相反的结论，每一次都是「尺子」坏了（见第四节）。

三、一次真实诊断的完整轨迹

场景 F8（多故障叠加：外部风控变慢 + order 内存泄漏）， 第 1 轮。下面是原样存档的工具调用与返回 —— 页面不替它修饰任何东西。

最终裁决

外部风控（payment 下游依赖）响应劣化：本窗口内 8049/8049 笔请求全部命中『外部风控响应缓慢』，单跳耗时约 800ms，占 payment 总耗时 818ms 的 98%，并沿调用链向上传导（inventory 899ms、order 1032ms）。这是本窗口内唯一能解释全链路延迟抬升的原因。；order 服务内存泄漏：leak_bytes_total≈4.22GB，在零报错、零失败、吞吐完整（各跳均 8049）的情况下持续增长。它与风控延迟无因果关系——去掉风控劣化它不会消失，去掉它风控延迟也不会消失，因此是一条独立的、需单独处置的问题。

四、诚实清单（刻意放在前面）

作废的题目

F2「连接池耗尽」：它声明的标准答案是「外部风控变慢是根因、池耗尽是症状」。 用对照实验一测——只把池改小、下游完全健康时，照样有 851 个 5xx； 而池保持 64、风控同样 800ms 时，5xx = 0。 ⇒ 那道题把答对的扣分、把答错的加分。已作废（保留为反例）。

被推翻过的结论（每次都是「尺子」坏了）

曾经以为真相性质
baseline 83.3%，多 Agent 有希望评分把「被否掉的提及」算作命中评分口径错
多 Agent 在 F2 上失败，命题被否定场景答案是反的，它答的才对题目错

口径边界（数字必须连同这些一起读）

  • 两侧样本：baseline 21 次尝试（7 场景 × 3 轮）；multi 21 次尝试（F1/F3/F4/F5/F6/F7/F8 × 3 轮）
  • 每侧仅 3 轮；只测 deepseek-flash（v4-pro 另做过一组对照， 见 docs/06）
  • 评分 = 关键词判定（主）+ LLM 裁判（独立交叉校验，不参与正确性计算）
  • 被诊断系统是自建的，不是生产系统 —— 故障是注入的，不是自然发生的
  • F4 上 multi 明显更差（1/3），两把尺子逐条核对过 —— 见 docs/harness-log.md #44
  • ⚠️ 幅度不稳定：给出的差距全部来自 F4 一个场景，而单场景每轮只跑 3 次 —— 同配置重跑 baseline，它在 F4 上自己就从 3/3 变成 2/3。三次配对实验里方向一致， 但幅度在 0~67 个百分点之间摆。所以本页给的是方向，不是幅度 —— 见 #46
