## 一、一页速览

### 它是什么

一个**可复现**的多 Agent 故障根因分析（RCA）实验：诊断一个自建的三服务系统，
并把**"测量本身可信"**当成第一目标 —— 包括诚实地报告一个**否定自己的结论**。

### 核心命题

> **LLM 的「自觉」不可靠 —— 所以用确定性的工程机制，同时约束它的判断和它的行动。**

| | 不可靠的"自觉" | 项目用的机制 | 现状 |
|---|---|---|---|
| **判断面** | 单视角确认偏误：先看到 CPU 飙升，就一路去找流量证据 | 信息隔离 + 强制交叉举证 | ✅ 已实现并被测量 |
| **行动面** | 模型"自己会小心" | 默认拒绝：ops 动作全过策略执行点（路径守卫 / 动词分级 / 隔离区 / 审计），并经 **MCP 收口** | ✅ **已接线**（诊断角色拿不到 ops 工具） |

### 最重要的结论是**负结果**

> **多 Agent 没有可测的价值增量 —— 更贵、更慢，而且没有任何准确率优势** ——
> 多花 **4.3 倍**的钱、**3.5 倍**的步数，准确率**低 4.8 个百分点**（按当前判据 95.2%；两侧覆盖**同样的 7 个场景 × 3 轮**）。
>
> ⚠️ **幅度要带上噪声带读**：那 9.5 个百分点全部来自 F4 一个场景，而单场景只有 3 次尝试 ——
> 同配置重跑 baseline，它在 F4 上自己就从 3/3 变成 2/3。
> 能站住的是**方向**（三次配对里 multi 一次都没超过 baseline），**不是幅度**（见 harness-log #46）。

但比结论更重要的是它**是怎么被保住的**：这个项目里我**八次**得到过相反的结论，
每一次查下去都发现是"**尺子**"坏了（评分口径 / 题目真值 / 任务定义 / 计价模型 / 测量工具）——
**第八次是反方向的**：我差点替多 Agent 开脱。
> 精确数字与证据索引见 [`docs/06`](06-多Agent结果.md)；八次翻案逐条见 `demo/rca-demo.html` 第四节。

### 它诊断什么

```
order → inventory → payment → 外部风控（模拟）
```

三个 FastAPI 服务 + Redis，`docker compose up -d --build` 一条命令起全栈；
**8 种可注入故障**，其中 F7 是合格的红鲱鱼、F8 是多故障叠加；
**每道题的标准答案都用绕开 LLM 的对照实验验过**（F2 因此被证明"答案写反了"并作废）。
> 详细目录（含"真值是否已验证"这一列）见 [`docs/04-故障目录.md`](04-故障目录.md)。

### 系统怎么搭的

```
Agent 编排（手写循环；LangGraph 未接线）
   ├─ baseline.py       单 Agent
   ├─ specialist.py ×3  三个专员：日志 / 指标 / 变更（工具面按角色隔离）
   └─ coordinator.py    交叉质证 + 裁决
        │  诊断工具：进程内只读调用；ops 工具：**经 MCP 收口**
   工具面：3 个只读工具 query_logs / query_metrics / get_changes
        │  只读遥测（原始遥测永不进上下文）
   遥测：接入 → 降维（压缩到 0.217%，信号全存活）
        │
   被诊断世界：三服务 + Redis + 8 种可注入故障
```

### 两个值得单独说的机制

1. **交叉举证是协议层的硬约束，不是提示词里的一句话。**
   工具结果产出 `evidence_id`，假设必须引用它 —— 协调者可以**机械地**执行举证责任：
   没引用证据直接驳回；引用的证据全在支持自己、没有一条能证伪他人，也驳回。
2. **"测量可信"本身是被工程化守住的。**
   —— 见下面「四、可信度是怎么被守住的」。

### 结论的边界（必须连同数字一起读）

- 两侧覆盖**同样的 7 个场景 × 3 轮**（样本对等）；但每侧只有 **3 轮**——
  轮间波动约 ±7 个百分点，所以"低 9.5 个百分点"要连同噪声带一起读
- 只测了便宜模型，**未测** `deepseek-v4-pro`
- 被诊断系统是**自建**的：故障是**注入**的，"根因"由我定义的判据裁定
- 交付的是**机制**，不是**保证**：任何守卫都可能被绕过

## 四、可信度是怎么被守住的（这个项目真正的重点）

> **项目规则：一条错误只有在回归用例能变红之后，才算封堵。**

这句话落到机制上是三件事：

1. **错误封堵清单**（[`docs/harness-log.md`](harness-log.md)）：
   每个错误记现象、根因、封堵措施、回归用例；**不许只写"已修"**。
2. **变异测试**：每个变异体把缺陷重新注回一份代码副本，用例必须变红，
   否则报 `NOT SEALED` —— 也就是"**代码修了，但测试抓不住**"会被区分出来。
3. **对账工具**：把清单里的"已封堵"声明与变异结果对上；
   还能发现"变异体悄悄过期"（源码重构后查找串失配、用例却仍在绿）。

此外还有几条同族的守卫：**冻结指纹**（防止对照实验的分母被无意改动）、
**可复现**（证据随仓库提交、页面可由存档重放）、
**README 与代码对账**（凡写到没实现的东西必须就地标明"未接线"）。

> 具体的条数、通过数、SEALED 数一律见 [`docs/00-状态.md`](00-状态.md) 的「当前事实」——
> 本页不复制，免得又多一份会过期的东西。

## 附：这个项目最想表达的一件事

> **我不承诺"AI 不犯错"，我交付的是"错误会留下痕迹、并且能被机械地发现"。**

如果只能记住一个数字，就记这个：**八次**。
八次我以为找到了"多 Agent 有用的证据"（其中一次是反的：我差点替它开脱），
八次都是我的尺子坏了 ——
而每一次都不是靠"我更仔细"，是靠在流程里加了**一个新的、能变红的检查**。
