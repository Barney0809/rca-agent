## 1. 项目定位

**名称**：`rca-agent`（RCA = Root Cause Analysis，SRE / 运维领域的标准术语）
**副标题**：多 Agent 根因定位与不可逆操作边界

> **一个多 Agent 系统：它既要能可靠地判断（定位真实故障的根因），也要能安全地行动（任何不可逆操作都必须经过独立于模型判断的确定性边界）。**

| 面 | Agent 的角色 | 要解决的问题 |
|---|---|---|
| **判断面** | 诊断者 —— 观察一个运行中的系统 | 多视角信号冲突时如何避免误判 |
| **行动面** | 行动者 —— 对系统执行操作 | 判断错了时如何保证不造成不可逆损失 |

副标题承担范围，主名保持稳定——名字跟核心交付物，不跟模块清单。

### 2.3 事故侧（真实触发）★

**2026-09-22 22:46**，一个被派遣的代码调研子代理执行 `Remove-Item -Recurse -Force`，删除了 **`D:\BarneyQ\Docs`**（使用者多年文档积累）。

**已取证确认的事实**：

| 项 | 结论 |
|---|---|
| 执行主体 | 三层委派链（主会话 → depth-1 → depth-2） |
| 直接机制 | 目标路径是"自己创建的乱码目录"；**PowerShell 5.1 读 UTF-8-no-BOM 脚本时把中文路径重编码**，导致路径解析失准，删除落到真实目录 |
| 为何不可逆 | `-Force` 绕过回收站 |
| 为何无法恢复 | D 盘无卷影副本、无系统保护、无文件历史；D 盘为 **NVMe SSD 且 TRIM 已启用**，数据块已回收 |
| 根本原因 | 派发者**未对删除操作设定任何路径边界**；已知的编码风险未被约束 |

**它给出的不是"一个 bug"，而是一整类需求：**

> **任何不可逆操作，都必须经过一个独立于模型判断的、确定性的边界。**

**同时它本身是高价值评测素材**：完整证据链、可追溯、根因唯一且已验证。

## 3. 核心命题

两个方向是同一命题的两面：

> **LLM 的"自觉"不可靠——所以要用确定性的工程机制，同时约束它的判断和它的行动。**

| | 不可靠的"自觉" | 确定性机制 |
|---|---|---|
| **判断面** | 单视角确认偏误 | 信息隔离 + 强制交叉举证 |
| **行动面** | 模型自己"会小心" | 路径/动词校验 + 不可逆操作默认拒绝 |

对应题库最高频的 **Harness Engineering** 与 **deny-first 权限模型**。

---

## 4. 成熟度目标 ★新增

区分"Demo"与"工程作品"的不是是否部署，而是下面这几层：

| 层次 | 含义 | 本项目目标 |
|---|---|---|
| **L0 玩具** | 玩具数据、只跑 happy path、单次运行、无 baseline | ❌ **明确避免** |
| **L1 可复现** | 一条命令起全栈；留出集；与 baseline 的对照数字；失败可复现 | ✅ **必需** |
| **L2 真实素材** | 含真实事故，非全部人造 | ✅ **必需** |
| **L3 持续运行** | 公开可访问、7×24 运行、会随时间漂移 | 🎯 **纳入计划** |
| **L4 有人依赖** | 他人实际使用 | ⭕ 尽力 |

> **L1 + L2 是"不是 Demo"的真正分界，且都不需要部署。** L3 是加分项，本项目纳入计划但排在核心之后。

## 6. 功能需求（FR）

### 6.1 诊断面

| 编号 | 需求 |
|---|---|
| FR-1.1 | 接入被诊断系统的遥测：日志（非结构化文本）、指标、变更事件 |
| FR-1.2 | **数据降维** —— 原始遥测**永不进入** Agent 上下文 |
| FR-1.3 | 专职 Agent 与**信息隔离** —— 日志/指标/变更三个 Agent，每个只能访问自己的数据源 |
| FR-1.4 | Coordinator 编排（supervisor 拓扑）+ **强制交叉举证**：假设必须能证伪其他假设，否则驳回 |
| FR-1.5 | 输出：根因 + 证据链 + 置信度 + 建议动作 |
| FR-1.6 | 场景包含**真实事故**（本案 + `fulearn` 真实故障史） |

### 6.2 行动面 ★（事故的直接转化）

| 编号 | 需求 |
|---|---|
| FR-2.1 | **所有工具调用必须经过策略执行点**，无旁路 |
| FR-2.2 | **路径规范化后再比对白名单前缀**，禁止直接使用未规范化的输入路径 |
| FR-2.3 | **编码安全** —— 路径全程 UTF-8；**禁止把路径交给 shell 二次解析** |
| FR-2.4 | 动词分级：`read` < `write` < `delete` < `move-outside` < `force` |
| FR-2.5 | 不可逆操作**默认拒绝**；授权需显式且**带 TTL** |
| FR-2.6 | **不存在硬删除** —— 删除 = 移入隔离区 + TTL；**不依赖任何操作系统的回收站机制** |
| FR-2.7 | 拒绝也记账（审计日志） |
| FR-2.8 | 拒绝须可解释：给出原因 + 建议的替代做法，不静默失败 |
| FR-2.9 | **策略执行点作为独立进程运行**，Agent 侧无直连文件系统的工具（工具面收口） |

**由 FR-2.6 引出的核心设计原则：**

> **把不可逆变成可逆，比"守住不可逆操作"更根本。**
> 事故无法挽回，不是因为守卫没拦住，而是因为**物理层面没有留下退路**。

### 6.3 可复现性 ★升为一等需求

| 编号 | 需求 |
|---|---|
| FR-C.1 | **被诊断系统自建、开源、自带故障注入**；一条命令起全栈（docker-compose） |
| FR-C.2 | 评测集与留出集随仓库提供 |
| FR-C.3 | **LLM 响应录制/回放**——访客无需 API Key 即可离线复跑评测 |
| FR-C.4 | 公开仓库无凭据、无私有依赖、无商业内容 |
| FR-C.5 | 任何人克隆后可在本地复现全部验收数字 |

> FR-C.3 是关键：**让面试官零成本、零门槛地自己验证你的数字。**

### 6.4 可靠性与恢复

| 编号 | 需求 |
|---|---|
| FR-3.1 | 循环级 checkpoint；进程被杀后可断点续跑 |
| FR-3.2 | Loop of Death 四层确定性防御：最大轮数 / token 预算 / 金额预算 / 连续无进展检测 |
| FR-3.3 | 重试具备幂等性 |

### 6.5 评测与回归

| 编号 | 需求 |
|---|---|
| FR-4.1 | 黄金集 + **留出集**（留出集调试期物理隔离，只用于最终评测） |
| FR-4.2 | 三维指标：**定位准确率 / 平均排查步数 / 单次成本** |
| FR-4.3 | **Scenario #0 = 本次事故**：给定会话日志与文件系统证据，推出根因 |
| FR-4.4 | **错误封堵清单**：每个 bad case → 一条永久回归用例；本次事故是第一条 |
| FR-4.5 | 与单 Agent baseline 的对照实验（**先做 baseline，再做多 Agent**） |
| FR-4.6 | 噪声带测量（重复跑，给出指标的波动区间，而非单次抽样） |

### 6.6 可观测性

| 编号 | 需求 |
|---|---|
| FR-5.1 | 全链路 trace：prompt / 思考 / 工具调用 / 观察 / 成本 / 延迟 |
| FR-5.2 | 任一 bad case 可一键回放 |
| FR-5.3 | 审计日志不可静默丢失（traceId 显式传递，不用 ThreadLocal） |

### 6.7 公开实例（L3）★新增

| 编号 | 需求 |
|---|---|
| FR-6.1 | 部署为公开可访问实例 |
| FR-6.2 | 访客可触发一次故障注入并观看多 Agent 实时定位 |
| FR-6.3 | **必须限流**（成本控制）——限流本身是功能，不是附加物 |
| FR-6.4 | 每次会话后可**一键重置**，防止状态污染 |
| FR-6.5 | 超限时给出明确说明与替代方案（本地复跑） |

## 7. 非功能需求（NFR）

| 编号 | 需求 | 判据 |
|---|---|---|
| **NFR-1** | 不可逆性最小化 | 系统不产生无法回滚的副作用（方向性目标，非可证性质） |
| **NFR-2** | **纵深防御** | 单层失守不致命；任一层独立可拦 |
| **NFR-3** | 成本可控 | 单场景成本可测可预算；有模型路由与缓存策略 |
| **NFR-4** | 可复现 | 见 FR-C |
| **NFR-5** | 可讲解 | 每个非显然决策有 ADR |
| **NFR-6** | **单一语言承载** | 全部用 Python；语言能力的举证责任完全落在 Python 工程质量上 |
| **NFR-7** | 可开源 | 无凭据、无商业内容 |
| **NFR-8** | 绝不接触生产 | 全部隔离环境；`fulearn` 只用本地库 |

> **NFR-6 的代价须明确**：没有第二语言可以分担"Python 精通"这句话——类型注解、async 正确性、包结构、测试覆盖必须当真，不能"能跑就行"。

## 8. 明确不做

**技术不做**：Go 及其他第二语言、向量库/RAG、微调、多模型横向对比、K8s/Istio、前端大屏、40+ 服务仿真、自建可观测栈（不引 Prometheus/Loki）。

**定位不做**：
- **不承诺"让 AI 不再犯错"**——无法交付的承诺；任何守卫都可被绕过
- **不作为"受害者叙事"**——事故是需求来源之一，不是项目主题

## 9. 验收标准

### 9.1 判断面

| 编号 | 标准 |
|---|---|
| AC-1 | 真实故障场景上，多 Agent 定位准确率显著高于单 Agent baseline（**含噪声带**） |
| AC-2 | 平均排查步数与单次成本可量化，且优于 baseline |
| AC-3 | 留出集结果独立可复跑，从未参与调试 |
| AC-4 | ≥3 个场景的症状位置与根因位置**跨越服务边界** |

### 9.2 行动面

| 编号 | 标准 |
|---|---|
| AC-5 | 越界删除尝试 **100% 被拒绝**，且理由可解释 |
| AC-6 | 编码异常路径不致解析失准（有针对性回归用例） |
| AC-7 | 删除操作可在隔离区**完整还原**——"不可逆"可被演示为"可逆" |
| AC-8 | 每次拒绝均有审计记录，无静默失败 |
| AC-9 | **Scenario #0 作为回归用例永久存在，且能变红** |

### 9.3 工程面

| 编号 | 标准 |
|---|---|
| AC-10 | 杀进程后可从 checkpoint 续跑（可录屏） |
| AC-11 | 错误封堵清单 ≥8 条，每条对应可自动运行的回归用例 |
| AC-12 | **陌生人克隆后一条命令起全栈，并复现全部数字**（含无 API Key 的离线复跑） |
| AC-13 | 公开实例可访问、可触发、有限流、可重置 |
| AC-14 | 每个非显然决策有 ADR，能支撑 40 分钟面试追问 |

## 10. 假设与风险

### 10.1 关键假设（任一不成立则方案重做）

| 编号 | 假设 | 风险 |
|---|---|---|
| A1 | 单次故障原始遥测规模**远超单个上下文容量** | 数据量太小则单 Agent 直接读完就赢，"多 Agent"沦为装饰 |
| A2 | 三个数据源之间存在**真实信息不对称** | 信号重叠则 Coordinator 沦为转发器 |
| A3 | 单 Agent baseline 存在**显著提升空间** | baseline 已很高则"提升"这个数字不存在 |
| A4 | 自建被诊断系统可在单机完整运行 | 依赖 docker-compose，需与 `fulearn` 的 MySQL 并行共存 |

### 10.2 风险

| 编号 | 风险 | 应对 |
|---|---|---|
| R1 | 多 Agent 退化为 prompt 串联 | 强制信息隔离 + 交叉举证；用 baseline 对照证明价值 |
| R2 | **L3 公开实例工期超支** | L3 排在核心之后；超时则降级为"本地一键起" |
| R3 | 造自建被诊断系统吃掉时间 | 用砍 Go 省下的时间对冲（约 1.5 天） |
| R4 | 只有"机制"没有"数字" | FR-4 从第一天就是需求，不是收尾工作 |
| R5 | 事故叙事喧宾夺主 | 见 §12 |
| R6 | 单语言项目语言能力无处藏 | 见 NFR-6 |

## 11. 关键决策记录（ADR）

### ADR-1　砍掉 Go
- **决策**：全部用 Python 实现，不引入第二语言。
- **理由**：① 严格按"必须"检验，没有一处是 Go 非做不可；② JD 语言要求"Java/Go/C++ 之一"已由 `fulearn` 的 Java 满足，Go 不加关键词分；③ "为什么用 Go"若答不硬，是净负分（"多而不精"）；④ 省下约 1.5 天投入评测与自建被诊断系统。
- **代价**：Python 成为唯一语言承载，工程质量举证责任上升（NFR-6）。

### ADR-2　被诊断对象自建，不用 `fulearn`
- **决策**：自建开源、可注入故障的被诊断系统；`fulearn` 降级为**真实素材来源**。
- **理由**：`fulearn` 闭源 → 面试官无法复现 → 直接破坏 L1（可复现），反而坐实"Demo"印象。
- **代价**：多约 1.5 天造系统，由 ADR-1 省下的时间对冲。

### ADR-3　事故作为需求来源与评测素材，不作为项目主题
- **决策**：事件出现在需求来源、行动面 FR、验收标准、错误封堵清单第一条；不出现在项目主题、卖惨叙事、口头承诺。
- **理由**：见 §12。

## 13. 与现有项目的关系

```
fulearn（商业项目，不可开源，已提审）
  ├─ 角色：真实素材来源 + 项目动机 + Java 深度证明
  ├─ 资产：Agent 循环 / 四重停止 / 调用链台账 / 多口径成本 / 评测体系
  └─ 空白：Multi-Agent / MCP / LangGraph / 沙箱权限  ← 本项目补齐

rca-agent（公开仓库，全 Python）
  ├─ 角色：诊断者 + 行动边界
  ├─ 被诊断对象：自建开源系统（可复现）
  └─ 素材：本次事故 + fulearn 真实故障史
```

**共同主线**：LLM 应用的可靠性工程——成本、护栏、可观测、评测。
