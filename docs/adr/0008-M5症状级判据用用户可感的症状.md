# ADR-0008：M5 的**症状级判据**用「用户可感的症状」，因果对齐的量只作解释

- **日期**：2026-09-27（D21/M5 症状级验证，**三轮** live）
- **状态**：已采纳
- **背景**：M5（自动修复闭环）只有**一个**"修好了吗"的结论位置。而在 **F4** 上，
  两个都能观测的量朝**相反方向**动（三轮 live，每轮 60 笔订单，证据见
  `runs/_evidence/` 下的 `m5-live-remediation.json`（第 3 轮）、
  `…-20260927-0006.json`（第 2 轮）、`…-20260927-0001.json`（第 1 轮））：

  | 量 | 故障态（retries=5） | 改回去后（retries=1） | 方向 |
  |---|---|---|---|
  | **成功订单数**（用户可感） | 56/60、52/60、55/60 | 21/60、22/60、16/60 | **更差** |
  | **每笔订单的下游调用次数**（与故障因果对齐） | 2.27、2.28、2.27 | 1.00、1.00、1.00 | 更好 |
  | 下游错误调用增量 | 80、85、81 | 39、38、44 | 更好（**但见下方口径**） |

  这不是噪声：Fisher 精确检验单边 `p = 5.3e-12` / `1.1e-08` / `6.5e-14`。

  ⚠️ **一个必须写清的口径**：错误调用从 80→39 看着像"失败变少了"，其实
  **单位调用的失败率始终在同一量级**（`0.59 → 0.65`、`0.62 → 0.63`、`0.60 → 0.73`）
  —— 主导变化的是**流量**（136/137/136 → 60 次调用）。
  世界的语义是 `attempts = max(1, retries)`（`world/common/downstream.py`），
  所以 **订单成功率 ≈ 1 - p^retries**：`1-0.588^5 = 0.93`（实测 0.933）、
  `1-0.650 = 0.350`（实测 0.350），三轮都在 **0.3–4 个百分点**内吻合。
  撤掉重试 ⇒ 放大消失，但 60% 上下的单次失败率**不再被摊平**。

---

## 决定 1：★ 判据 = **用户可感的症状**（成功订单数）；因果对齐的量只作**解释**

**决定**：`verify(symptom="成功订单数", ..., lower_is_better=False)` 是唯一的 ★ 判据。
「每笔订单的下游调用次数」「下游错误调用增量」**只当诊断量**，看着好看/难看都不单独下结论。

**理由**：M5 要回答的问题是「这次自动修复**对系统有没有好处**」，
而不是「我有没有改动我打算改的那个旋钮」—— 后者由**读回确认**单独负责，已经分开了
（#60：动作生效 ≠ 症状修好）。拿"与故障因果对齐的量"当判据，会把
**"动作生效"伪装成"问题解决了"**：这次实测正好给了反例 —— 动作生效 ✓、放大降了 2.3× ✓、
而订单成功率从 **93% 掉到 35%**。

**代价**：会得出"（对用户）更差"这种难看的结论，并且必须接受一个反直觉的真实结果：
**修了被记录的根因，症状反而更差**。F4 就是这个形状 —— 被撤掉的 `downstream_retries`
在放大流量的同时也在**兜住**单次失败，它是**缓解措施与故障机制的同一条旋钮**。
本 ADR 接受这个代价：宁可报告一个难看的真相，也不报一个好看但答非所问的结论。

---

## 决定 2：两把尺子**必须同时报**，分歧要显式标出来

**决定**：★ 判据与因果对齐的量方向相反时，脚本与证据**都要**把两边一起写出来，
并置 `metrics_disagree = true`（纯函数，有用例 + 变异体）。

**理由**：只报用户侧会漏掉"故障其实被削弱了"（读者不知道动作有没有用）；
只报因果侧会把灾难说成修复（#61 就是这一类）。**分歧本身就是最有信息量的东西** ——
与 D10 那两把尺子（关键词 / LLM 裁判）的处理原则一致。

**代价**：结论更长、更难一眼看懂；对外讲述时必须解释"为什么两个数字朝相反方向走"。

---

## 决定 3：判据的**口径**必须写进证据与输出，不许只活在调用方的脑子里

**决定**：每条判据都要显式带上：

- **方向**（`lower_is_better`）—— #61：写死"越小越好"会把「10 → 0」报成 `improved`；
- **两态信号**（前置检查 `precheck_metric_signal`）—— 故障态本来就没症状时，
  "修好了"是**没有依据**的结论（#63 当场拦下过一次）；
- **覆盖率**（`patch_coverage`）—— **故障补丁 ≠ 变更记录**：补丁是"实际改了什么"，
  变更记录只是"现实世界里会留痕的那部分"。两者差额就是"这次只能修到几分之几"，
  必须在**动手之前**算出来、点名未覆盖的旋钮、并指向人的那扇门
  （F4 实测就是 `1/2 = partial`：`payment.risk_error_rate` 没有记录）；
- **样本量**与"只看方向、不看幅度"的边界 —— 成功数落到 **0 是地板值**，
  仍然有信号（方向可读、幅度不可读）；
- **结局标签**（`remediation_outcome`）必须**自描述**：`action-ok-symptom-worse-partial-coverage`
  一目了然；旧词表里对 `worse` 只写 `action-ok-symptom-partial`，
  读者会把它读成"部分改善" —— 那正是本 ADR 要防的软措辞。

**理由**：这一轮出现的三个缺陷（#61 方向、#62 类型、#63 假故障态）**全都在"判据/测量"这一层**，
而不是在"动作"那一层。判据的口径必须随证据一起存档，否则下一个人无法复核。

## 落地约束（要有守卫，不能只写在文档里）

- `scripts/remediate_demo.py` 的 `metrics_disagree`、`patch_coverage`、`remediation_outcome`
  必须是**纯函数** + 用例 + 变异体（#64：`metrics_disagree` 原来写在 `main()` 里，
  只靠"跑一次 live 看一眼"验证）；
- 前置检查不许被绕过：两态无信号 ⇒ `exit 5`、不下结论（有变异体 `rem-f`）；
- 覆盖率不许被粉饰：若实现把"没覆盖到的那一半"藏起来（`rem-l` 就是重演这个），用例必须变红；
- 结局标签不许丢掉症状状态（`rem-m` 就是把标签压回"动作跑了就算好"）；
- 证据 JSON 必须同时含三把尺子的 `status`、`lower_is_better`、`precheck`、
  `coverage` 与 `metrics_disagree`；
- ⚠️ **本 ADR 的结论只在 F4 上被实测支持**（一个故障、`deepseek-flash`、每轮 60 笔、**三轮**）。
  换故障或换指标时要重新走一遍"两态都有信号 + 因果对齐 + 覆盖率"这三道检查。
