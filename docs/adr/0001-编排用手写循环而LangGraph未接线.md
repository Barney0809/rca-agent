# ADR-0001：编排用「手写循环」，LangGraph **未接线**（并如实标出来）

- **日期**：2026-09-25（D15 补记；实现贯穿 D5~D7）
- **状态**：已采纳（**部分内容为"刻意未做"**，见下）
- **背景**：技术选型阶段把 **LangGraph 1.2.12** 列为首选，理由写在
  `docs/02-技术方案与排期.md`：JD 提及率最高的编排框架、显式状态机便于讲述、
  原生 checkpointer 能解决断点续跑。但真正实现 Agent 时，编排是**手写循环**
  （`src/rca/agents/baseline.py` / `specialist.py` / `coordinator.py`），
  `langgraph` 在代码里**零命中** —— 只有 `pyproject.toml` 里一行依赖。

---

## 决定 1：当前编排用显式 Python，不引入图框架

**决定**：三条路径（单 Agent / 三个专员 / 协调者）都用手写的显式控制流。

**理由**：

1. **这个任务的控制流是固定的两段**：专员各自调查（互不通信）→ 质证 → 裁决。
   没有"按中间结果动态决定下一步做什么"的需求，图的表达力用不上。
2. **我要的核心机制是领域逻辑，不是编排逻辑**：
   "假设必须引用 `evidence_id`，否则机械驳回" —— 这类**举证责任校验**写在显式
   Python 里可以被逐条测试、也能对着面试官讲清；写进图节点里只是换了个位置。
3. **可测性**：`tests/test_agents.py` 可以直接对函数断言；
   若藏在图的状态机里，多数用例要先装配图才能跑。

**代价（必须承认）**：

- **没有 checkpointer ⇒ 断点续跑（AC-10）做不了** —— 而这正是当初选 LangGraph 的主要理由之一；
- 换句话说：**选型时写的理由，实现时没有兑现**，这一点必须在对外文档里标明（见下）。

---

## 决定 2：不接线的部分**必须写在明处**（这条是硬规矩）

**决定**：凡是"设计里有、实现里没有"的东西，README 与对外文档必须**就地**标明
"未接线/未实现"。

**背景（一次真实事故）**：README 的架构图曾经写着
`Agent 层（LangGraph） │ MCP │ 策略执行点（独立进程）` —— **三条一条都不成立**，
而它就这么挂了一个多月（harness-log **#41**）。来源是我把 `docs/02` 的**设计图**
抄进了 README，实现后来偏离了，而文档体系里"设计"与"实现"没有任何区分标记。

**代价**：写起来更啰嗦，首页要留一栏专门写"没做的"。

**为什么仍要这么做**：一个把没做的写在首页的项目，比一个只在角落标一句的项目可信；
而且被追问"给我看看你的 state graph"时，**穿帮的代价远大于承认没做**。

---

## 决定 3：什么时候应该改这个决定

出现下面任一条时，就该把 LangGraph 接进来：

- 需要 **断点续跑**（AC-10）—— 这是最直接的理由，checkpointer 是现成能力；
- 控制流开始**依赖中间结果**（例如"证据不足就回头换策略再查一轮"这种真正的循环规划）；
- 需要**人机中断/审批**（人在回路里批准某个动作）。

在此之前，接图只是为了"技术栈列表好看"，属于典型的**用框架解决不存在的问题**。
