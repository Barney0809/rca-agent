# 错误封堵清单（Harness Log）

> **这个文件的用途**：每一次真实的失败，都必须变成一条**永久回归用例**。
>
> 原则（Harness Engineering）：**不要靠改 prompt 让系统少犯错，要把每次犯错工程化到"它物理上再也不可能犯"。**
> 所以这个清单不是事故记录，是**已经不可能再发生的错误列表**——每加一行，系统就少一类失败。
>
> 格式：现象 → 根因 → 封堵措施 → 回归用例 → 状态

---

## 📏 收录判据（**不是所有错误都该记**）

「什么都记」会让这份清单失去意义 —— 它就不再是"已不可能再发生的错误列表"，
而变成一本流水账。所以入库要过两道筛子。

### 筛子一：这个错误的性质是什么？

| 性质 | 记不记 | 理由 |
|---|---|---|
| **平台陷阱**（编码、时区、路径语义） | ✅ | 会以**不同形式**反复出现 —— #3 就是同一根因的第三次 |
| **方法论缺陷**（测试盲区、验证不充分） | ✅ | 会让**一整类**缺陷漏网，危害大于单个 bug |
| **设计缺陷**（静默失败、缺触发条件） | ✅ | 正是本项目要防的核心 |
| **纯操作失误**（引号、括号、敲错命令） | ❌ | 即时反馈已经抓到；"工程化"它没有意义 |

### 筛子二：它是"响亮地失败"还是"静默地留下后果"？

**这一条比第一条更准。**

    响亮失败（语法错误、命令非零退出）→ 你当场就知道了 → 不需要清单
    静默后果（测试全绿但功能坏了）    → 你可能永远不知道 → **必须进清单**

本项目已收录的绝大多数条目（#4 #5 #6 #9 #10）都是**静默**类。
这不是巧合 —— **静默失败是唯一需要工程化防守的失败形态。**

### 一个必须承认的边界

有些过程缺陷**无法用代码测试封堵**（见下一节）。对它们，
只能靠**流程纪律**——而纪律依赖注意力。

本项目对这个边界的处理原则是：

> **不要指望纪律覆盖所有地方，而是尽量缩小"必须靠纪律"的面积。**
> 能自动化的自动化，不能自动化的写清楚，剩下的如实标注为"靠人"。

## 🧰 工作过程缺陷（**流程封堵，不是代码封堵**）

上面 8 条都是"系统里的缺陷"。下面两条是**我的工作过程**里的缺陷 ——
它们不在代码里，所以不能用代码测试守住，只能改流程。

### P1　用错误的解释器运行脚本 → 得到误导性结论

**日期**：2026-09-24（D0）

**现象**：写完依赖验证脚本后，我用 `python`（系统解释器）运行它，输出是：

```
FAIL langgraph  ModuleNotFoundError: No module named 'langgraph'
FAIL langchain_core  ...
（12 个依赖全部 FAIL）
```

**看起来**：依赖一个都没装，环境搭建失败。

**实际**：依赖全都装好了，只是装在 `.venv` 里。
`uv sync` 装的是项目虚拟环境，而我用的是系统 Python。

**为什么它属于"静默"类**：命令成功执行、退出码正常、输出看起来完全合理。
**它给出的是一个错误的事实，而不是一个错误。**
如果我没多想一步，就会得出"环境搭建失败"的错误结论并去重装依赖。

**封堵措施（流程）**：

| 措施 | 位置 |
|---|---|
| 运行脚本一律显式写项目解释器：`.\.venv\Scripts\python.exe`，不写裸 `python` | `AGENTS.md` 第 1 条 |
| 首选 `uv run python ...` —— 它自动用项目环境 | `README.md` / `Makefile` |
| `scripts/dev.ps1` 在自检开头就打印**实际使用的解释器路径** | `scripts/dev.ps1` 第 1 节 |

**为什么不能自动化**：要自动检查"调用方是否用了对的解释器"，
需要拦截每一次外部调用 —— 成本远超收益。
而上述三条措施把出错概率降到很低，且一旦出错会在**第一行输出**里暴露出来。

- [x] 流程已固化
- [x] 自检脚本会打印实际解释器（让错误立刻可见）
- [ ] **无自动检查** —— 如实标注：这一条靠人

### P2　批量替换时把新值写重复 → 静默产生重复内容

**日期**：2026-09-24（D2）

**现象**：用 `edit` 的 `replace_all` 替换 `docker-compose.yml` 里的 `W_REDIS_URL` 时，
我在 `new_string` 里**不小心把同一行写了两遍**。结果三个服务各多出一行重复的
环境变量。提交成功、YAML 合法、容器正常启动 —— **一切看起来都对**。

**为什么它属于"静默"类**：没有报错，没有异常输出。唯一的暴露方式是**读回文件**。

**封堵措施（流程）**：

| 措施 | 说明 |
|---|---|
| `replace_all` 之后**必须读回文件确认** | 这是本次得以发现的唯一手段 |
| 替换前后用 `grep` 对比目标行的数量 | 本次即如此：`W_REDIS_URL` 从 3 处变成 6 处，一眼可见 |

**可以部分自动化的地方**：重复行检测。
但 `docker-compose.yml` 里合法的重复结构很多（同样是 `networks: [rca]`），
写一条"禁止连续重复行"的检查会大量误报，反而让检查被忽略。
**权衡后不自动化**，改为流程要求。

- [x] 流程已固化（改完读回 + 计数对比）
- [ ] **无自动检查** —— 如实标注：这一条靠人

### 关于这两条的共同点

它们都是**我的操作**，不是系统的缺陷。所以：

- 它们**不产生代码回归用例**（没有代码可测）
- 它们的封堵方式是**改工作流程**
- 它们的价值是**提醒下一轮的我（或另一个代理）**：

> **对"看起来没报错"的操作，要多一步确认。**
> 本次两个静默缺陷（P1、P2）都是这样被抓到的 —— 不是靠日志，
> 而是靠"读回结果"这个动作。

## #1　误删工作目录之外的真实目录（不可恢复）

**日期**：2026-09-22 22:46

### 现象

一个被派遣的代码调研子代理在清理自己的临时目录时执行了 `Remove-Item -Recurse -Force`，删除目标是"自己创建的乱码目录"，实际落到了工作目录的**兄弟目录**——一个从未被授权触碰的真实目录。

### 根因链（四环，每一环都本可拦住）

| 环节 | 缺陷 |
|---|---|
| 1 | 派发者未对删除操作设定**任何路径边界**（无"不许越出工作目录"的约束） |
| 2 | 目标路径依赖**编码错乱的目录名**，路径解析失准 |
| 3 | `-Force` **绕过回收站**，拆掉了系统自带的最后一道网 |
| 4 | 该磁盘**无卷影副本、无系统保护、无文件历史**，且为 NVMe 且 TRIM 已启用 → 数据块被回收 |

**损失**：**无**——被挡住，但这次挡住靠的是纪律，不是机制

### 现象

`scripts/dev.ps1` 用工具写入（UTF-8 **无 BOM**），内容含中文提示语。在 Windows PowerShell 5.1 下执行时报语法错误：

```
Missing closing '}' in statement block or type definition.
+  if ($failures -gt 0) { Bad "$failures 涓緷璧栨棤娉曞鍏? }
```

源代码中的中文 `个依赖无法导入` 被解析成 `涓緷璧栨棤娉曞鍏?`——**乱码中的字节吃掉了引号，破坏了语法结构。**

### 根因

**与本清单 #1 完全相同的机制**：

> Windows PowerShell 5.1 把 UTF-8 **无 BOM** 的脚本文件按系统 ANSI（简体中文为 GBK）读取，任何非 ASCII 文本都会被 mangle。

#1 里它让"路径解析"错位；#2 里它让"语法解析"错位。**同一个根因，两种表现。**

### 封堵措施

| 措施 | 说明 |
|---|---|
| **可执行脚本一律纯 ASCII** | `.ps1` / `.bat` / `Makefile` 中不允许出现非 ASCII 字符；中文只允许出现在 `.md` 文档中 |
| 脚本头部显式注明 | `scripts/dev.ps1` 头部写明"本文件必须保持纯 ASCII"及原因 |
| 自检脚本包含此项 | `scripts/dev.ps1` 的安全自检段 |

### 回归用例

- [ ] CI 检查：所有 `*.ps1` / `Makefile` 必须为纯 ASCII（`D1` 加入）
- 断言：任何提交的 PowerShell 脚本中不存在字节 > 0x7F

### 状态

- [x] 封堵（改用纯 ASCII 重写，已通过执行验证）
- [ ] 自动化回归（D1 加入 CI）

> **这条为什么值得单独记录**：它证明了 #1 的根因**不是偶然**，而是**可复现的结构性缺陷**——只要还有脚本在中文环境下用非 ASCII，它就会以第三种、第四种形式再出现。
> 同时也证明了"靠纪律"是不够的：#2 之所以损失为零，是因为有人在盯；**必须变成自动检查。**

## #4　下游 4xx 被当成成功返回（静默吞错）

**日期**：2026-09-24
**损失**：无（在开发期发现），但**是一类会隐藏故障的严重缺陷**

### 现象

压测时发现：order 明明收到 inventory 的 `409 库存不足`，却返回了 **`CONFIRMED`**：

```json
{"status":"CONFIRMED", "detail":{"detail":"库存不足"}}
```

失败被当成成功上报。

### 根因

`world/common/downstream.py` 里判断写错了：

```python
if resp.status_code >= 500:        # ← 只把 5xx 当错误
    raise DownstreamFailed(...)
return resp.json()                  # ← 409 于是被当成成功返回
```

4xx 是"下游明确拒绝"，被当成了正常响应。

### 为什么它危险

**静默吞错比直接报错危险得多**：
- 上游据此报出成功状态
- 指标里 `5xx = 0`，看起来一切正常
- 排障时会被引向完全错误的方向

本次正是它掩盖了另一个问题（见下），让"故障注入不生效"这个假象持续了很久。

### 封堵措施

| 措施 | 说明 |
|---|---|
| 区分 `DownstreamRejected`（4xx）与 `DownstreamFailed`（5xx/超时） | 前者**不重试**（重试无意义），但**必须原样上抛** |
| 上游把 `DownstreamRejected` 映射为**同样的状态码与原因** | 不再伪造成功 |

### 回归用例

- `tests/test_offline.py::test_regression_4_downstream_4xx_is_rejected_not_success`
- `tests/test_offline.py::test_regression_4_4xx_must_not_retry`

- `tests/test_world.py::test_f2_does_exhaust_pool_and_show_503`（端到端：4xx 语义在真实链路上成立）

## #6　日志解析漏掉整整一类行（占 21%，且含关键证据）

**日期**：2026-09-24（D3）
**损失**：无（开发期发现），但**会让降维结果不可信**

### 现象

降维报告显示：`未解析行数 6058（占 21.1%）`。

排查后发现被漏掉的是**第三方库写的日志**：

```
2026-09-24 04:59:22.064 INFO  HTTP Request: POST http://inventory:8000/reserve "HTTP/1.1 502 Bad Gateway"
```

这是 `httpx` 库自己的 logger 写的 —— 有时间和级别，但**既没有 `[service]` 段，
也没有 `trace=` 段**（它不是我们的 logger adapter 写的）。

### 根因

解析正则要求日志必须包含 `[service]`：

```python
r"\[(?P<service>[^\]]+)\]\s+"     # ← 写死了必填
```

于是这一整类行被判定为"无法解析"，只被计数，不进模板聚合。

### 为什么它危险

**这些行不是噪声，是证据。** `502 Bad Gateway` 正是"下游不可用"的直接观测。
如果降维把它们丢掉，Agent 就看不到那一层的失败 —— 而它恰好是判断
"故障发生在哪一层"的关键。

**更危险的是它很难被发现**：`未解析行数` 只是一个统计数字，如果不盯着看，
降维照常输出、报告照常漂亮，只是**悄悄少了 21% 的信息**。

### 封堵措施

| 措施 | 说明 |
|---|---|
| `[service]` 段改为**可选** | 三种变体（有 service+trace / 只有 service / 两者都无）都能解析 |
| 无 service 标记时回退到调用方传入的服务名 | 采集层是按服务分别读取日志的，所以能确定归属 |
| 保留"未解析行数"统计 | **它是这类问题的唯一暴露途径**，不许去掉 |

### 回归用例

- `tests/test_offline.py::test_regression_6_third_party_log_lines_are_parsed`
  （三种日志变体全都要能解析）
- `tests/test_offline.py::test_regression_6_unparsed_lines_are_counted_not_silently_dropped`
  （真正无法解析的行必须能被识别，而不是静默丢）

### 状态

- [x] 已修：未解析比例 **21.1% → 0.0%**
- [x] 回归用例已落地（9 条离线用例全绿）
- [x] **已证明能变红** —— 变异测试：把 `[service]` 段改回必填，
      用例立刻报 `这一行没能解析：'... HTTP Request: POST ... "HTTP/1.1 502 Bad Gateway"'`；
      还原后确认与提交版本逐字节一致

> **这条的元教训**：解析层**必须统计"自己没读懂多少"**。
> 一个只报告成功率的解析器，会把"读不懂"伪装成"不存在"。
> 本项目这条规则后来写进了 `reduce.py` 的设计：**未解析行数显式进 ReducedView**。

## #7　loadgen 超发 53%（数据量不可复现）

**日期**：2026-09-24（D2）
**损失**：无，但会让**需求假设 A1 的验收依据不成立**

### 现象

目标 1200 个请求，实际发出 **1841** 个（超 53%）。

### 根因

请求数上限**只在监控循环里检查**，而那个循环每 5 秒才醒一次：

```python
while not stop.is_set():
    await asyncio.sleep(5)          # ← 5 秒里可以发出几百个请求
    if total() >= max_requests:
        stop.set()
```

而有些场景（如 F2 池耗尽）跑得慢，5 秒只发几十个；有些场景跑得快，
5 秒能发上千个 —— **超发量随场景大幅波动**，于是"同样参数两次跑出不同数据量"。

### 为什么它危险

`单场景日志量 ≥3 万行` 是假设 A1 的验收标准。
如果请求数本身不可复现，**日志量也不可复现，这条验收就无法成立**。

### 封堵措施

请求数上限改为**由 worker 自己检查**（每次请求前看一眼），不再依赖监控循环：

```python
while not stop.is_set() and time.perf_counter() < deadline:
    if _total(stats) >= max_requests:
        stop.set()
        return
```

**理论上界**因此变为 `max_requests + concurrency`
（停止信号发出时，每个 worker 可能正在处理一个请求）。

### 回归用例

- `tests/test_world.py::test_regression_7_loadgen_respects_max_requests`
  故意把监控循环调到 30 秒才醒一次 —— 若 worker 不自己检查，必然超发

### 状态

- [x] 已修
- [x] 回归用例已落地
- [x] 证明方式：用例把 `poll_s` 设成 30 秒，若停止只依赖监控循环则必然超出上界

## #10　还原时传空 id → 内部崩溃而非可解释拒绝

**日期**：2026-09-24（D4）
**损失**：无

### 现象

`restore(quarantine_id=None)` 抛出 `TypeError`：

```
TypeError: expected string or bytes-like object, got 'NoneType'
```

### 根因

调用方在上一步"删除被拒"时，拿到的 `Decision.quarantine_id` 是 `None`
（被拒了当然没有隔离项）。它把 `None` 直接传给了 `restore()`，
而 `restore()` 把 `None` 交给了正则做格式校验。

**一个内部崩溃，而不是一条可解释的拒绝。**

### 为什么它违反项目原则

项目的核心命题是"**拒绝必须可解释**"（FR-2.8）。
一个 `TypeError` 堆栈不是解释 —— 它既没有说明原因，
也没有给出下一步该怎么做，而且**不会进审计**。

### 封堵措施

对外接口先校验入参类型，返回带理由与建议的 `Decision`（并写审计）：

```python
if not quarantine_id or not isinstance(quarantine_id, str):
    return Decision(allowed=False, reason="还原需要一个有效的隔离项 id…",
                    suggestion="先确认上一步的「删除」真的被放行了…")
```

### 回归用例

- `tests/test_policy.py::test_regression_10_restore_with_missing_id_is_a_clean_denial_not_a_crash`
  （`None` / `""` / `123` 三种输入都要得到干净的拒绝，且拒绝进审计）

## #11　噪声带算错：把"单次尝试只能对或错"伪装成了统计量

**日期**：2026-09-24（D5）
**损失**：无（会让人误判 baseline 的稳定性）

### 现象

第一次跑完整评测，报告显示：

```
① 准确率   61.1%    噪声带 0.0%–100.0%
```

**0% 到 100%** 这个"噪声带"看起来像"波动极大"，其实毫无信息量。

### 根因

`_band()` 被作用在**每一次尝试的真假值**上：

```python
accs = [i.correct for i in self.attempts]     # [True, False, True, ...]
"accuracy_band": self._band(accs)              # min/max → [0, 1]
```

单次尝试的结果只能是 `True` 或 `False`，所以 min/max 必然是 `[0, 1]`。
**它反映的是"布尔值只有两种取值"这个事实，而不是轮与轮之间的波动幅度。**

正确的做法是：**先算每一轮的聚合准确率，再看这些轮之间的极差**。

### 为什么它危险

它把**一个常数**伪装成了**一个统计量**。

后果：你会以为"波动是 0%–100%"（无法解读），而真实情况是
"各轮 67% → 33% → 83%，波动 50 个百分点"（可直接解读、可直接行动）。

一个不能被解读的数字，比没有数字更糟 —— **它占着位置，让人以为已经量化过了。**

### 封堵措施

```python
by_round: dict[int, list[Attempt]] = {}
for a in self.attempts:
    by_round.setdefault(a.round_no, []).append(a)
round_acc = [sum(1 for a in items if a.correct) / len(items) for items in by_round.values()]
"accuracy_band": self._band(round_acc)
```

**顺带加了 `--from-json` 入口**：聚合逻辑改了之后可以从已保存的原始尝试记录
重新聚合，**不必再花一遍钱重跑 LLM**。这也是"把原始数据留全"的价值。

### 回归用例

- `tests/test_eval.py::test_regression_11_noise_band_is_over_rounds_not_attempts`
  **关键设计**：构造"第 1 轮 100%、第 2 轮 50%"。
  旧实现对单次尝试求极差 → `[0, 1]`；新实现按轮聚合 → `[0.5, 1.0]`。
  **两者结果不同**，所以这条用例能真的区分实现。
  （如果只断言 `band == [0,1]`，新旧实现都会通过，那就什么也没测。）
- `tests/test_eval.py::test_regression_11_band_is_not_always_zero_to_one`
- `tests/test_eval.py::test_regression_11_band_functions_exist_for_cost_and_steps_too`

### 状态

- [x] 已修
- [x] 回归用例已落地（3 条）
- [x] **已证明能变红** —— 变异测试：把 `_band(round_acc)` 改回 `_band(accs)`，
      3 条用例中有 2 条立刻失败；还原后确认与提交版本一致

> **本条与 #4、#9、#10 是同一个模式**：**静默的错误结论**。
> 它不报错、不崩溃，只是给出一个看起来专业、实际无意义的数字。

### P3　提交信息里的双引号被 PowerShell 截断（**已踩两次**）

**日期**：2026-09-24（D2 第一次，D5 第二次）

**现象**：`git commit -m $msg` 报出一堆奇怪错误：

```
error: pathspec '不掉陷阱的结论。' did not match any file(s) known to git
error: pathspec '把「布尔值只有两种取值」这个事实伪装成了统计量。' did not match any file(s) known to git
（一长串）
```

**看起来**：git 不认识这些"文件"。

**实际**：PowerShell 5.1 把含 `"` 的字符串传给**原生命令**时，
会重新拼命令行 —— 内嵌的双引号把字符串截断了，
后半段被当成**独立参数**传给了 git。

**为什么它容易被漏掉**：`git add -A` 那一步**是成功的**，
所以工作区看着"已经准备好了"，只有 `git commit` 失败。
而错误信息埋在几十行输出里，不主动核对 `git log` 就很难发现。

### 封堵措施（流程）

| 做法 | 说明 |
|---|---|
| **提交信息用 `-F <文件>` 传，不用 `-m <字符串>`** | 从根上避开引号与换行的传递问题 |
| 写完 `-F` 文件后**核对 `git log`** | 确认提交真的产生了 |
| 同一原则适用于任何传给原生命令的**长文本**（不限于 git） | 字符串里有引号 / 换行 / 非 ASCII 时一律走文件 |

### 为什么它不自动化

要自动拦截"所有传给原生命令的字符串里有没有引号"，需要包一层命令执行器 ——
成本远超收益，而且会破坏正常的交互式使用。
**三条流程措施已把出错概率降到很低，且失败必然可见（`git log` 一查就知道）。**

- [x] 流程已固化
- [ ] 无自动检查（如实标注）

> **它与 P1、P2 的共同点**：都是**工具使用方式**的问题，不是系统缺陷。
> 而且都指向同一个根因家族 —— **PowerShell + 引号/编码 + 非 ASCII**。
> 这个家族在本仓库已经贡献了 #1 #2 #3 #9 P1 P3 共六条记录。
>
> **在这个环境下工作，"路径/文本的编码与转义"是最高频的风险源。**

跑 D6 的专职 Agent（场景 F6，只有内存泄漏）时，MetricsAgent 给出：

1. 场景驱动在**窗口开始前**和**结束后**各抓一份指标快照，

## #13　随手定的 `max_steps` 实质性地改变了"准确率"

**日期**：2026-09-24（D5 复测时发现）
**损失**：**D5 的第一版数字第二次作废**

### 现象

同样六种场景、同样 3 轮，只改一个参数：

| `max_steps` | 准确率 | 收敛率 | 噪声带 |
|---|---|---|---|
| **8**（第一版随手定的） | 77.8% | 83% | 67%–83% |
| **14** | **83.3%** | **100%** | 83%–83% |

差异几乎全部来自**一个场景**：

```
F3  在 max_steps=8  时：0%   ← 三轮全部"跑完 8 步没给出结论"
F3  在 max_steps=14 时：100% ← 三轮全部答对，平均用 9 步
```

### 根因

`max_steps=8` 是**我随手定的一个数**，没有依据。
而 F3（本环节处理变慢）恰好是**唯一 `5xx = 0` 的场景** ——
没有任何 ERROR 可找，Agent 会一直挖，需要的步数天然更多。

于是"步数预算不足"被记成了"准确率低"。

### 为什么它危险

它把**两个完全不同的东西混进了同一个数字**：

    「推理错了」      —— 这是模型的归因能力问题
    「没跑完就停了」  —— 这是工程配置问题

前者要靠多 Agent / 更好的方法解决；后者只要把参数调大就好了。
**把它们混在一起，会让后续所有比较失去意义** ——
你无法判断"多 Agent 提升了 5%"是因为协作更好，还是因为预算变了。

### 封堵措施

| 措施 | 说明 |
|---|---|
| 用**收敛率**做前置门槛 | 收敛率不到 100% 时，准确率这个数字不可用于比较 |
| 步数预算按**实测需要**定，不靠拍脑袋 | 先跑一次看最慢的场景需要多少步，再定上限 |
| 报告里**同时给出**收敛率与步数分布 | 让人能看出"失败是因为错还是因为没跑完" |
| 报告里对低轮数**显式告警** | 已在 `print_report` 里实现（轮数 < 3 时提示噪声带不可信） |

### 回归用例

- `tests/test_eval.py::test_regression_13_aggregate_exposes_convergence_and_parse_rates`
- `tests/test_eval.py::test_regression_13_report_warns_when_accuracy_is_not_comparable`
  **这是核心**：报告不只是"给出"收敛率，还必须在它不足时**主动指出问题** ——
  因为读者会把一个被配置污染的准确率当成模型的真实能力，再去和多 Agent 比较。

- `tests/test_eval.py::test_regression_13_warns_on_too_few_rounds`

## P4　脚本打印非 ASCII 时崩溃，把整段结论一起丢掉

**日期**：2026-09-24（D7）
**损失**：无（当场发现）。但这类错误**专挑最后一步发作**，代价被放大过。

### 现象

新写的变异检查脚本 `scripts/mutate_check.py` 第一次运行，
在**打印结果的那一行**抛：

```
UnicodeEncodeError: 'gbk' codec can't encode character '\u2713' in position 2
```

它**已经跑完了全部检查**（包括两次 pytest、对照组、变异体），
只因为要打印一个 `✓` 就崩了 —— 整段输出和结论全没了，看起来像"脚本是坏的"。

### 根因

本机控制台代码页 936。`sys.stdout` 接**真实控制台**时 Python 走 `WriteConsoleW`，不受代码页限制；
但接**管道/文件**时（上层采集输出）退回 `cp936`，编不出的字符直接抛异常。

这是同一个编码机制的**第 4 次**不同后果：

| 次序 | 后果 | 条目 |
|---|---|---|
| 1 | 路径解析错位 → **删除了一个真实目录（不可恢复）** | #1 |
| 2 | 脚本语法解析错位 → 脚本崩溃 | #2 |
| 3 | 数据解析错位 → PowerShell 读 JSON 失败 | #3 |
| 4 | **输出编码错位 → 整段输出与结论丢失** | P4 |

### 封堵措施

**关键的一步是"先做实验，再做决定"。**

第一版凭直觉写成 `reconfigure(errors="replace")`，并配了一段注释说
"不要用 `encoding="utf-8"`，那会让 GBK 控制台里的中文变成乱码"。
这个论断**听起来很合理，但是错的**。于是写了 `scripts/probe_stdout_encoding.py`，
在真实管道下把三种写法各跑一遍（这个探测脚本**留在仓库里**，面试官可重跑验证）：

```powershell
.\.venv\Scripts\python.exe scripts\probe_stdout_encoding.py none      # -> CRASH（exit 1）
.\.venv\Scripts\python.exe scripts\probe_stdout_encoding.py replace   # -> 不崩，但中文乱码
.\.venv\Scripts\python.exe scripts\probe_stdout_encoding.py utf8      # -> 中文与 emoji 都正常
```

| 兜底写法 | 中文 | emoji | 结论 |
|---|---|---|---|
| 完全不兜底 | GBK 字节 | **崩溃** | ❌ |
| `reconfigure(errors="replace")` | 仍是 GBK 字节 → 上层按 UTF-8 读全是乱码 | `?` | ❌ 不崩，但读不成 |
| `reconfigure(encoding="utf-8", errors="replace")` | 正常 | 正常 | ✅ |

结论：**必须同时给 `encoding` 和 `errors`**。
仓库里另外 6 个脚本**早就**是这个写法（说明这个坑以前踩过、当时改对了），
我加的那 6 处反而既重复又更弱 —— 已全部改回原状（`git diff -- scripts` 为空）。

另外修掉了两处自己埋的坑：

- 变异副本原本放在 `runs/_mutants/`。而 `tests/test_offline.py` 的 #3 编码检查
  用"路径里出现 `runs` 就跳过"排除目录，于是把副本里**所有文件**都跳过了，

## #23 / #24 / #25　D9：把"打转"和"手误"变成可见、可校验的东西

**日期**：2026-09-25（D9）
**损失**：无（三条都是**把隐性问题变成可见**，没有造成金钱或数据损失）

三条合在一起写，因为它们来自同一轮工作：**让"看不见的问题"变得看得见。**

### #24　打转不可见：14 步 87 次工具调用，分不清"深挖"还是"原地转"

**现象**（实测，改任务定义之后）：

```
[F1 第1轮] ❌ 步数=14 工具=87 成本=¥0.0405 31.9s
      结论：（空）
```

报告里只能看到"步数 14、结论为空" —— **分不出它是在深挖，还是在原地打转。**

**为什么这很要紧**：两者的修法**完全相反**。

| 判断 | 该修什么 |
|---|---|
| 在深挖 | 加步数预算 |
| 在打转 | 加预算只会让它更贵地打转 —— 得改提示词或工具返回的内容 |

**封堵**（三层，全部落在 `ToolBox.call` —— 工具调用的唯一出口，所以每个 Agent 自动具备）：

1. **统计**：参数**完全相同**的调用记为 repeat；不同（工具+参数）组合记为 distinct
2. **提醒模型**：第 3 次重复起在工具返回里追加警告；第 5 次起明确要求收手
3. **分类**：`stop_reason` 把"撞预算"与"疑似打转"分开，并各自指向不同的修法

**两个设计细节值得单独记**：

- **签名要比"解析后的参数"，不能比原始字符串。**
  模型经常把同一个查询换个空格或键序再发一遍 —— 那正是打转的典型样子，
  按原文比会把它当成"新证据"。
- **"已经问过什么"的状态必须放在 `RunContext` 上，不能放在 `ToolBox` 上。**
  放 box 上的话，"同一个 ctx 建了两个 box"（比如有人把 `box = ToolBox(ctx)`
  挪进循环）会让检测**静默失效**，而 `repeat_calls` 仍然是 0 ——
  **看起来就像"没有打转"。一个看起来正常的 0 比一个明显的错误更危险。**
  这条已配了专门的回归用例（`test_two_boxes_over_the_same_context_still_detect_repeats`）。

### #23　编辑手误把函数"吞"进上一个函数（三次）

而那段文本里混着模型的**推理过程**，不是它的**结论**。

```

   → 再给一次机会；仍失败才按原样接受
```

三个调用点（baseline / 专职 Agent / 交叉质证）**共用同一份逻辑**
（`src/rca/agents/contract.py`）—— 复制三份迟早会走散，

否则就成了"引导它答对"，那是在作弊。**有用例专门守这一条。**

     M demo/rca-demo.html          # 而 git diff 是空的！

也就是说：**陌生人克隆后只要重跑一次生成器，自己的仓库就"脏"了**，
而 `git diff` 又什么都看不到 —— 他会以为是自己环境的问题。

### 根因

`.gitattributes` 第 4 行写着 `* text=auto eol=lf`（第 1 行注释说明了理由：
"避免跨平台协作时'整文件都被改动'的噪音"），
而 Python 的文本模式**在 Windows 上默认把 `\n` 翻译成 `\r\n`**：

    OUT.write_text(html_text, encoding="utf-8")        # ← 平台默认换行

⇒ 生成器写出来的字节与仓库里的（LF）不一致，git 认为文件被改过。

**这就是 `.gitattributes` 想避免的那种噪音，只不过来源不是"另一个人的编辑器"，
而是我自己的生成器。** 讽刺的是：我写 `.gitattributes` 正是为了这件事，
却在写生成器时忘了它同样适用。

### 封堵措施

    OUT.write_text(html_text, encoding="utf-8", newline="\n")

⚠️ 这条**只在 Windows 上是必需的**（Linux 的默认换行本来就是 `\n`）——
对应的变异体在 Linux 上是空操作。本项目只在 Windows 上跑（见 `AGENTS.md`），
所以这个守卫是有意义的；换平台时应当知道它的适用范围会变。

- `test_demo_generator_writes_lf_so_a_fresh_clone_stays_clean` —— 跑一遍生成器，

| 运行 | 调用数 | 命中率 | 构成（命中/未命中/输出） |
|---|---|---|---|
| 第 1 次 | 33 | **79.5%** | 2.0% / 25.7% / **72.3%**　← 文档引用的就是这一次 |
| 第 2 次 | 24 | 75.3% | 1.6% / 26.2% / 72.2% |
| 第 3 次 | 26 | 79.1% | 1.9% / 24.6% / 73.5%　← 默认取到的"最近一次" |

⇒ **文档的数字是对的，但它指向的是一次具体运行，而那段录音是追加的。**
文件每被追加一次，"最近一次"就不再是文档引用的那一次了 ——
于是那句"零成本可复现"实际上**复现不出来**。

（顺带印证了 #33 的记载：第 1 次 33 个调用、第 2 次 24 个 —— 与"我拿 33 次和 33+24 次比"
这件事完全吻合。旧账对上了。）

### 根因

`cost_breakdown.py` 只有两个口径：**最近一次**与**整文件**。
而文档引用的是"某一次历史运行" —— **这个口径工具根本表达不了**。

**这依然是 #37/#38 的同一族的第五种形态**：
一句看起来可核对的话，实际上没有任何人能核对 —— 因为**工具里没有那条路径**。
区别在于：前几次是"证据不在""结不了"，这次是**取不回来**。

### 封堵措施

给 `cost_breakdown.py` 加上两个口径：

- `--run N` —— 指名道姓取第 N 次运行（从 1 开始），报告里打印
  「当前统计范围：第 N 次运行（文件里共 M 次）」；
- `--list` —— 列出每一次运行的调用数、命中率与构成，让读者先看清有哪几次。

并把切段逻辑抽成 `split_runs()`（可按段取用），构成计算抽成 `composition()`。
**越界要明确报错**（`--run 9` → 退出码 2），绝不悄悄退化成"最近一次" ——
那是最坏的一种假绿：读者以为拿到了文档引用的那次，其实拿到了别的。

### 回归用例

`tests/test_deliverable.py`（4 条）：`--run 1` 取回第 1 次（断言输出 600 tok 而非默认那次）、
`--list` 列出全部、越界报错、非整数报错。
变异：`cost_breakdown_segmentation` 增至 2 个变异体（新增"选择器差一"：
`--run 1` 悄悄变成第 2 次）。

### 状态

🟢 **已封堵** —— 现在在干净克隆里 `--run 1` 能精确复现文档里的 79.5% / 72.3% / ¥0.0586。

> 🎯 这一条是**"按自己写的复现步骤走一遍"**才发现的问题。

## #42　冻结指纹对换行敏感 —— 那条"守卫"在**每个干净克隆里都是红的**

**日期**：2026-09-25（写 D14 时，在**真克隆**里跑全套测试发现的）

### 现象

README 里我写了一句"零成本核对：`uv run pytest` 全绿"。
为了不写假话，我在**干净克隆**里真跑了一遍全套 —— 结果：

    1 failed, 189 passed, 1 skipped

    FAILED tests/test_agents.py::test_baseline_module_is_frozen
      expected: ba2fe0cb321bb615
      actual  : 5a5e5f1978330d11

**代码没改**，指纹却变了。原因：那条指纹是

    digest = hashlib.sha256(path.read_bytes()).hexdigest()[:16]

直接对**字节**取哈希。而本仓库的 `.gitattributes` 规定 `* text=auto eol=lf`：

| 位置 | `baseline.py` 的换行 | 指纹 |
|---|---|---|
| 我的工作副本（Windows，编辑器/生成器写过） | CRLF | `ba2fe0cb321bb615` |
| **干净克隆**（`.gitattributes` 说了算） | LF | `5a5e5f1978330d11` |

⇒ 这条"冻结"用例在**每一个干净克隆里都红**。
（顺带说明：我在**自己的仓库里**反复跑了几十遍都没发现 —— 因为它在我这儿永远是对的。
这跟 #37 的"空白格"、#38 的"skip 也是绿"是同一件事：**只有换个人来跑才会现形**。）

### 根因

**指纹守错了东西。** 它想守的是"`baseline.py` 的**内容**有没有被改"，
而实际守的是"**字节**有没有变" —— 字节里包含一个与内容无关的平台变量（换行符）。

⚠️ 这里有个容易想岔的地方：`.gitattributes` **解决不了**它。
它管的是入库/检出的字节，而 `read_bytes()` 读的是**磁盘上此刻**的字节 ——
任何编辑器、生成器（见 #39）随时可能写出另一种换行。

### 封堵措施

指纹逻辑抽成 `scripts/frozen_fingerprint.py`，并且**先把 CRLF 归一化成 LF 再算哈希**：

    hashlib.sha256(raw.replace(b"\r\n", b"\n")).hexdigest()[:16]

抽成独立模块的理由：这样"与平台换行无关"这件事**可以被单独测试**
（留在用例里就只能靠真克隆来体现，而真克隆没人天天跑）。
指纹值随之更新为 `5a5e5f1978330d11`（**内容没改，改的是算法**），
理由写在 `tests/test_agents.py` 的变更日志里。

### 回归用例

`tests/test_deliverable.py::test_frozen_fingerprint_ignores_line_endings`：

- 同一内容、LF 与 CRLF 两种字节 ⇒ **必须**算出同一个指纹；
- 内容真的变了（`b = 2` → `b = 3`）⇒ **必须**算出不同指纹
  （否则这个守卫就成了摆设 —— 归一化不能把守卫一起归掉）。

变异：新组 `platform_hygiene`（去掉归一化 ⇒ 用例变红），SEALED。

### 状态

🟢 **已封堵** —— 现在干净克隆里全套测试**真的全绿**（我跑过才敢写进 README）。

> 🎯 这条是最典型的"**只有换个人来跑才会现形**"的缺陷，而它同时说明另一件事：
> **README 里那句"全绿"，如果不是在干净克隆里真跑过，就又是一句不可核对的话。**
> 我本来是去"核对一句自己要写的话"，结果核出来一个已经存在一个多月的坏守卫。
>

> **把文档里的每一句话拿到代码/环境里去对**，比通读文档有用得多。

## #46　差点把一个 3 轮样本的**幅度**当成稳定结论

**日期**：2026-09-25（D15，做 v4-pro 对照实验时顺带撞出来的）

### 现象

D15 主跑（7 场景 × 3 轮）得到 multi **90.5%** vs baseline **100%**，
差异**全部来自 F4 一个场景（multi 1/3，baseline 3/3）**。
我据此写了"**准确率还低了 9.5 个百分点**"，并把它放进了 README / 讲述稿 / 总览 / 页面。

随后做 ④（换模型对照）时，顺手做了一个**同一预算下的 2×2**（都放宽到 `--max-steps 40`）：

| F4 单场景（各 3 轮） | baseline | multi |
|---|---|---|
| flash @22（**主跑**） | 3/3 | **1/3** |
| flash @40 | **2/3** | **2/3** |
| v4-pro @40 | 3/3 | 2/3 |

⇒ **方向一致**（multi 三次配对里没有一次超过 baseline），
但**幅度在 0 ~ 67 个百分点之间摆** —— 而每个格子的样本量只有 **3**。

也就是说：我引用的"9.5 个百分点"是**一个 n=3 格子的差值**，
而同配置重跑（flash baseline）自己就从 3/3 掉到了 2/3。

### 根因

**把"方向"当成了"幅度"。** 单场景 3 轮下，一个格子的准确率只能取 {0, 33, 67, 100}，
相邻两档之间差 33 个百分点 —— 这种量级的分辨率**根本撑不住 9.5 这样的精度**。
（本项目早就知道"噪声带"这件事：#11 还专门修过噪声带的算法，
但那是**轮间**的；这次是**单场景样本量**的问题，是另一回事。）

### 封堵措施

1. **措辞降级**（所有对外文档）：从"更差 9.5 个百分点"改成
   「**没有换来任何优势**；唯一失败场景的幅度不稳定，只敢说方向、不敢说幅度」；
2. **把 2×2 对照与它的结论写进 `docs/06`**，与主跑数字并列 ——
   读者能看到"这个数是从哪来的、它稳不稳"；
3. **给运行器加一条小样本告警**（可测的那一半）：当"场景数 × 轮数"给出的
   单场景样本量 ≤ 3 时，报告里必须打印一句
   「单场景 n≤3 ⇒ 该场景的准确率不可作为结论」，把这件事从"我记得"变成"工具自己说"。

### 回归用例

`tests/test_eval.py`：`test_small_sample_warning_fires_for_three_rounds` /
`test_small_sample_warning_is_silent_for_a_big_sample` —— 直接测那个判定函数。

### 状态

🟡 **已更正措辞、已加工具告警**；但"多少样本才够"这件事**没有定论**

## #53　`--mode replay` 从来没有真正跑通过 —— 而它被当成"已实现的能力"写进了文档 🟡

**日期**：2026-09-25（D19）
**性质**：**文档说了假话**（同 #37/#41 一族），且这次是**我自己写的验收话术**

### 现象

`--mode replay` 的实现、用例、文档全都齐了 —— 但**从来没有完整跑过一次**。
第一次真跑，第一步就 miss：

```
RuntimeError: 回放模式下未命中录制（tag='baseline/r-20260924-054323', model='deepseek-flash'）
```

### 根因（两层，第一层是结构性的）

| 层 | 事实 |
|---|---|
| **key 里嵌着场景目录名** | key = `sha256(tag + model + messages)`，而 multi 的 tag 形如 `specialist/metrics/r-20260925-072345` —— **`r-…` 是一次故障注入产生的时间戳**。换一批场景目录 ⇒ key 必变 ⇒ 第一步就 miss |
| **录制只在 record/replay 模式下才创建** | `live` 模式的运行**什么都不录**。所以"拿 live 时代的录制去重放"是**一场注定 miss 的假实验**（我第一次就是这么试的） |

⇒ 「零成本重放」的完整前提不是"有录制文件"，而是
**录制 + 同一批场景目录（同名同内容）**。场景日志 24.1 MB，gzip 后 2.6 MB（约 9:1），
于是有了 `runs/_replay_pack` 与 `scripts/make_replay_pack.py`。

### 决定性证据：零 API 调用是**实测**的，不是推断的

把环境毒化后重放（假 Key + `DEEPSEEK_BASE_URL=http://127.0.0.1:9`，该端口无人监听）：

```
exit=0  wall=20s
F1 第1轮 ✅ 步数=30 工具=139 …  (21 次尝试全部命中，7 场景 × 3 轮)
```

**任何一次真实调用都会立刻失败** ⇒ 跑完就等于没走过网络。
（`provider.chat` 里 replay 模式未命中即抛错，所以"偷偷退回真实调用"这条路径在结构上也不可达。）

### 但接着抓到了更值钱的一件事：回放**不等于**复现归档那一次

同一批录制响应，归档 `multi-20260925-131953`（`mode=record`）判 **19/21**，
回放判 **21/21**；而且**步骤数就不一样**（21 次里有 **13 次**不同，例如
F1 第2轮 27→30、F5 第3轮 30→26、F8 第2轮 25→33 —— 左=归档、右=回放），
F4 的第 1、3 轮判定翻转（❌→✅）。

先怀疑"同一个 key 被后来的运行覆盖"，**实测否定了**：643 个 key，**0 个重复**。
真原因是：录制文件里混了 **4 次 record 运行**（094934 / 095817 / 100336 / 131953）的响应，
回放只能挑到**录制内部自洽的那一条轨迹** —— 它不保证是你归档的那一次。

> ⇒ **回放不能用来复现"某一次具体运行"**，只能证明"这套代码 + 这批场景 + 这批响应
> 会稳定地给出某个结论"。要让回放对齐归档数字，必须做到 **一批录制 = 一次运行**（未做）。

### 顺带被门禁抓住的一条：回放不得冒充测量

`docs/00-状态.md` 开头写着"**唯一权威**：进度、当前事实"。可它自己漂了三处：

| 位置 | 写着 | 实际 |
|---|---|---|
| 「当前事实」 | `254 passed / 1 skipped` | **255 passed**（这一小时加了 1 条用例） |
| D9 交付行 | "当前全仓 **27 组 / 60 个**，全部 SEALED" | **39 组 / 91 个** |
| 复跑清单 ④ | 交付物用例 `✅ 24 passed` | **28 条**（D17–D19 期间这个文件长大了） |

第三处是**守卫自己抓出来的**：我人工扫了一遍 md，只发现了前两处。

### 根因

数字是**手工维护**的，而它分散在"当前事实"、交付行、复跑清单里 —— 每加一条用例、
每加一个变异组，就有三处需要人记得改，且**没有任何东西会因此报错**。

### 封堵（不是"我下次记得"，而是让漂移直接变红）

新增 `tests/test_status_numbers.py`，四条：

1. 用例数 ← 子进程实测 `pytest --collect-only` 的收集数（按 node id 数，并与汇总行交叉核对）
2. 交付物用例数 ← 同一次收集里的 `tests/test_deliverable.py` 条数
3. 变异数 ← `scripts/mutations.json` 的真实条目数
4. 封堵条数 ← `docs/harness-log.md` 总览表（**含"变异证明 / 靠人"的拆分**）

两个设计点：

- **每条守卫都先断言"我读到了东西"，再比大小** ——
  否则解析器一坏就退化成"什么都没读到 ⇒ 一切正常"（#26 踩过的空绿）。
- **同一条不变量的重复副本一律改成指针**：D9 行里那句"当前全仓 …"改成
  "当前计数见本节开头的「当前事实」——本行不复制，复制必漂"。
  这与 harness-log 自己的做法一致（本文档从不复制当前计数）。

### 变异体（4 个，全部 SEALED）

| 变异体 | 证明什么 |
|---|---|
| `status-a` 文档写 999 passed | 守卫真的在读文档，不是自说自话 |
| `status-b` 把 D9 期的 38 组 / 90 个写回文档 | 变异数守卫不是恒真 |
| `status-c` 只改总数、不动拆分 | 守卫必须把三个数字都对齐 |
| `status-d` 总览表解析器**静默丢掉最后一条**（少算一条，页面看起来完全正常） | 守卫依赖的"计数口径"本身也被守着 |
| ⚠️ 设计这个组时的两个**被否决**的变异体 | 「放宽扫描范围」与「去掉去重」**都恒绿** —— 实测：去重存在时二者都不改变结果集合。变异检查器当场判 NOT SEALED，两次之后才换成上面那条。**变异体自己也得真的能红**，否则等于没封堵 |

## #55　护栏第一版：**坏答案一条没抓到，好答案误伤 7 条** —— 三个根因都是我规则写错 🟢

**日期**：2026-09-25（D21，用户提案"在别的 Agent 运行时诊断它、防止它犯错"）
**性质**：**设计被测量打回来**（不是代码 bug，是判据设计错了）

### 背景

按 ADR-0007 的四条决定做了护栏 M1：判定核心（纯函数）+ 自家参考适配器 +
零成本双侧验证。三条规则的第一版是这么设计的：

| 规则 | 意图 |
|---|---|
| `unsupported_claim` | 结论点名的具体标识符必须在轨迹里出现过 |
| `unbased_metric` | **旗舰规则**：被当作根因的指标必须有参照 —— 冲着 #44 那个真缺陷去的 |
| `unverifiable_number` | 测量数字必须可溯源（防幻觉数字） |

### 实测（21 次归档尝试，**零 API 成本**）

```
坏答案 2 次，护栏报出 0 次      ← 一条真缺陷都没抓到
好答案 19 次，护栏报出 7 次     ← 误伤
```

三个根因，**全部是我的规则写错**（逐条查出来的，不是猜的）：

| # | 现象 | 真根因 | 修法 |
|---|---|---|---|
| 1 | F4 的真缺陷**漏报** | `stock_level{sku=...} = …` 三个 **SKU** 的三个值被当成"这个指标有 3 个值 ⇒ 有参照" | 按**序列**（名字 + 标签）判基线：只有**同一序列**出现第二个值才算 |
| 2 | 结论写"零 `ERROR`"被报 **block** | `ERROR` 是**日志级别**，却被当成"点名了指标名" | 收紧到 **snake_case**（含下划线）+ 一张词表；日志级别/格式名/异常类名都排除 |
| 3 | `3.2`、`4.22GB` 被判成幻觉数字 | ① 模型会**四舍五入**（4433/1400 = 3.166 → "3.2"），1% 容差恰好差一点；② **单位换算**没处理（证据里是 `4.22e+09` 字节） | 判定改成"**舍入相等**"（比放宽容差更紧）+ 单位倍数换算 |

### 修完再测

```
上线两条规则：21 次真实尝试 0 误伤（19 个正确结论全部静默）
注入形式缺陷：注入前 0 条 → 注入后 block + 2 条   ✅
```

### 旗舰规则被**降级**：精确率 1/15 ≈ 7%

`unbased_metric` 确实抓到了 F4 的真缺陷（报出 `stock_level` —— 那正是 #44 里被错误提升成
根因的那个无基线指标），但**19 个正确结论里它报了 14 个**：

- F8 的正确答案点名 `leak_bytes_total`，而泄漏确实是真故障 —— 只是指标只有一个采样值。

⇒ 判它"无基线"在形式上是成立的，在语义上是**错怪**。修不好：

> 区分"该不该拿这个指标当主根因"本质是**配权判断**，需要知道哪个原因才是真的
> = **需要标准答案** = 超出护栏的表达力。

**这就是 ADR-0007 决定 1 的测量版证明** —— 那条决定原本只是推理，现在有数了。
处置与 #44 一致：**保留为诊断量**（`DIAGNOSTIC_RULES`），不参与 `judge()`。

### "必须触发"那一侧怎么验（真实归档里没有形式缺陷）

F4 那两次真坏答案坏在**配权**上，形式规则看不见（见上）。所以这一侧用**确定性注入**：
把一条干净轨迹的结论改写成"点名了一个不存在的指标 + 报了一个查无此数的值"。

这跟 ADR-0007 决定 3 说外部 Agent 的验证方式（**注入已知错误才有 ground truth**）
是同一个做法，只不过这次在轨迹层面做。

### 封堵状态：🟢（形式面已封堵，边界如实标出）

| 项 | 状态 |
|---|---|
| 用例 | ✅ 12 条（`tests/test_guard.py`） |
| 变异体 | ✅ 5 个全部 SEALED：只上线数字规则 / 让缺结论退化成空列表 / 舍入判定恒假 / 基线忽略标签 / **注入函数变成空操作**（门禁本身也要被门禁） |
| 结构性守卫 | ✅ 护栏**不许 import 评分侧**（AST 扫 + `SCENARIOS` 字样检查）+ "换个错的答案判定不变"的行为守卫 |
| ⬜ 一条**没有**变异体背书的不变量 | 日志级别那条是**双机制冗余**（正则要求下划线 + 词表），单点变异打不红它 —— 如实写在这里，不硬凑一个变异体 |
| ⬜ 抓不到配权类错误 | **M1 只判定、不拦截**；`block` 目前是一句结论，真正阻断工具调用是 M4 |

## #56　M2 软提醒（证据审查者）：机制、一次真事故、以及 2×2 实测 🟢

**日期**：2026-09-25 ~ 09-26（D21/M2）
**性质**：新能力 + **实测给出的是一个中性偏正的结论**

### 一、为什么要它（以及它的三条铁律）

M1 的硬规则在 21 次真实轨迹上 **0 次触发** —— 它们只抓形式缺陷。
想让结论**更准**，只能靠软层：让 Agent 在交卷前被问一句"你这条证据在哪"。

三条铁律（ADR-0007 决定 2）：
**只提醒不拦** / **不进判分** / **最多 3 条意见、只修正一次**（不迭代 ——
第二次起就是自己说服自己，成本也失控）。

### 二、机制层（已封堵）

| 不变量 | 为什么 |
|---|---|
| **fail-safe** | 新增的 LLM 调用路径坏掉**不能**作废整轮 —— 三个专员 + 质证 + 裁决的钱已经花掉（#15 的教训） |
| **"没审成" ≠ "没问题"** | 解析失败/异常必须留 `error`，不能悄悄返回空意见（#26 的空绿） |
| **审查意见只进"修订输入"** | 以"附在同一条 user 消息后的后缀"形式进入裁决，`correct` 只看结论文本 |
| **前/后留档** | 只存修订后的结论就回答不了"修订帮了还是害了" ⇒ 记 `pre/post_revision_correct`、`revision_helped/hurt` |

用例 `tests/test_reviewer.py`（8 条，全离线）· 变异组 `guard_soft_review`（4 个，全 SEALED）。

### 三、实测时撞上的一次真事故（**不是**代码缺陷，但暴露了真缺陷）

```
openai.APIStatusError: Error code: 402 - {'error': {'message': 'Insufficient Balance'}}
```

护栏开臂在**第一次尝试的专员调用**上就断了（还没走到审查者）。
当天两次跑法各撞一次，第二次才跑完。**它暴露的真缺陷是**：

> 崩溃会让**已经花钱跑完**的尝试一起丢掉 —— `run()` 抛异常时 `main()` 走不到存档那一步。
> 真实场景是"跑完 20 次、第 21 次撞上 402" ⇒ 20 次的钱和结果全没。

修法：单次尝试失败**跳过并继续**；401/402/403 判为**致命**（立刻停，但把已完成的尝试留在
report 里并写 `aborted_reason`）；其余当抖动。
用例 `tests/test_runner_resilience.py`（7 条）· 变异组 `runner_survives_api_errors`（3 个，
其中一个**故意重演原始事故**：abort 时清空已完成的尝试）。

### 四、2×2 实测（同一次会话、同一计价时段、同参数）

| | 臂 A 护栏关 | 臂 B 护栏开 |
|---|---|---|
| 尝试 | 21 | 21 |
| 答对（存档判据 = 当前判据） | **20/21 = 95.2%** | **21/21 = 100%** |
| 成本 | ¥1.5172 | ¥1.7739（**+16.9%**） |
| 步数 / 工具调用 | 613 / 1991 | 604 / 1920 |
| 审查触发 / 修订 / 审不成 | — | 21/21（每次 3 条）/ 21 / 0 |
| **修订帮了 / 帮了倒忙** | — | **1 / 0** |

存档：`runs/_eval/multi-20260925-234207`（关）、`runs/_eval/multi-20260926-001536`（开）。
逐场景**只有 F4 有差异**（A 2/3、B 3/3），唯一翻转的格子是 **F4:1**。

#### 三条口径（缺一条就会读错）

1. **臂间差异不能算"更准"**：差 1 格，而两臂是**非配对**样本，且 3 轮测不出幅度 ——
   D15 同一配置自己就从 86% 抖到 100%。**方向都谈不上，只能说"没有变差"。**
2. **真正的证据是那条配对记录**：`revision_helped=1 / revision_hurt=0` ——
   同一次尝试内部的前后对照，不需要跨臂比较。它说明软提醒**能把被判错的结论改成对的**，
   而且 21 次里**没有一次把对的改错**（这条 0/21 是实打实的）。
3. 判定用的是**关键词判据**；裁判口径这次没跑。

#### 一个我怀疑过、又查证否定的点

**现象**：21 次**每次恰好 3 条**意见 —— 很像在凑 prompt 里写的上限。

**查证**（抽 F1/F5/F8 各一轮读原文）：不是凑数。它抓到的是
*「协调者仍在用**已被该专员撤回**的断言支撑结论」*、
*「把**观测缺失**说成**已证否**；『去掉风控延迟它不会消失』是**反事实断言**，材料里没有干预观测」*、
*「连接池未贴顶只能排除连接池饱和这一项，推不出……」* —— 这类真问题，
而且都落在具体主张与具体缺口上。

#### 结论（如实）

> **软提醒不做坏事（21 次里 0 次把对的改错）、偶有正收益（1 次把错的改对）、代价 +16.9%；
> 收益是否值这个价钱，3 轮样本答不了。**

⇒ 定位是**可选能力，默认关闭**（`--guard`）。继续往前走需要**更多轮次**
（把 1/21 的配对记录变成可信方向）与**裁判口径的第二把尺子**，而不是更多的规则。
