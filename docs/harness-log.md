>

## #1　误删工作目录之外的真实目录（不可恢复）

**日期**：2026-09-22 22:46
**损失**：`D:\BarneyQ\Docs`（使用者多年文档积累），**不可恢复**

### 现象

一个被派遣的代码调研子代理在清理自己的临时目录时执行了 `Remove-Item -Recurse -Force`，删除目标是"自己创建的乱码目录"，实际落到了工作目录的**兄弟目录**——一个从未被授权触碰的真实目录。

### 根因链（四环，每一环都本可拦住）

| 环节 | 缺陷 |
|---|---|
| 1 | 派发者未对删除操作设定**任何路径边界**（无"不许越出工作目录"的约束） |
| 2 | 目标路径依赖**编码错乱的目录名**，路径解析失准 |
| 3 | `-Force` **绕过回收站**，拆掉了系统自带的最后一道网 |
| 4 | 该磁盘**无卷影副本、无系统保护、无文件历史**，且为 NVMe 且 TRIM 已启用 → 数据块被回收 |

### 封堵措施

| 措施 | 说明 |
|---|---|
| **路径规范化后比对白名单前缀** | 见需求分析 FR-2.2。禁止直接使用未规范化的输入路径 |
| **编码安全** | 路径全程按 UTF-8 处理；**禁止把路径交给 shell 二次解析**（FR-2.3） |
| **隔离区替代硬删除** | 删除 = 移入隔离区 + TTL，可还原。**不依赖任何操作系统的回收站机制**（FR-2.6） |
| **不可逆操作默认拒绝** | 需显式授权，且授权带 TTL（FR-2.5） |
| **拒绝也记账** | 每次拒绝写入审计，不静默失败（FR-2.7 / FR-2.8） |

### 回归用例

- `AC-5` 越界删除尝试 100% 被拒绝，且理由可解释
- `AC-6` 编码异常路径不致解析失准
- `AC-7` 删除操作可在隔离区**完整还原**

### 状态

- [x] 需求已固化（需求分析 §6.2）
- [ ] 实现（D4）
- [ ] 回归用例（D4）

## #2　同一编码机制在本项目脚本中复现（被守则拦住）

**日期**：2026-09-22（同一晚）
**损失**：**无**——被挡住，但这次挡住靠的是纪律，不是机制

### 现象

`scripts/dev.ps1` 用工具写入（UTF-8 **无 BOM**），内容含中文提示语。在 Windows PowerShell 5.1 下执行时报语法错误：

```
Missing closing '}' in statement block or type definition.
+  if ($failures -gt 0) { Bad "$failures 涓緷璧栨棤娉曞鍏? }
```

源代码中的中文 `个依赖无法导入` 被解析成 `涓緷璧栨棤娉曞鍏?`——**乱码中的字节吃掉了引号，破坏了语法结构。**

### 根因

**与本清单 #1 完全相同的机制**：

> Windows PowerShell 5.1 把 UTF-8 **无 BOM** 的脚本文件按系统 ANSI（简体中文为 GBK）读取，任何非 ASCII 文本都会被 mangle。

#1 里它让"路径解析"错位；#2 里它让"语法解析"错位。**同一个根因，两种表现。**

### 封堵措施

| 措施 | 说明 |
|---|---|
| **可执行脚本一律纯 ASCII** | `.ps1` / `.bat` / `Makefile` 中不允许出现非 ASCII 字符；中文只允许出现在 `.md` 文档中 |
| 脚本头部显式注明 | `scripts/dev.ps1` 头部写明"本文件必须保持纯 ASCII"及原因 |
| 自检脚本包含此项 | `scripts/dev.ps1` 的安全自检段 |

### 回归用例

- [ ] CI 检查：所有 `*.ps1` / `Makefile` 必须为纯 ASCII（`D1` 加入）
- 断言：任何提交的 PowerShell 脚本中不存在字节 > 0x7F

### 状态

- [x] 封堵（改用纯 ASCII 重写，已通过执行验证）
- [ ] 自动化回归（D1 加入 CI）

> **这条为什么值得单独记录**：它证明了 #1 的根因**不是偶然**，而是**可复现的结构性缺陷**——只要还有脚本在中文环境下用非 ASCII，它就会以第三种、第四种形式再出现。
> 同时也证明了"靠纪律"是不够的：#2 之所以损失为零，是因为有人在盯；**必须变成自动检查。**

## #4　下游 4xx 被当成成功返回（静默吞错）

**日期**：2026-09-24
**损失**：无（在开发期发现），但**是一类会隐藏故障的严重缺陷**

### 现象

压测时发现：order 明明收到 inventory 的 `409 库存不足`，却返回了 **`CONFIRMED`**：

```json
{"status":"CONFIRMED", "detail":{"detail":"库存不足"}}
```

失败被当成成功上报。

### 根因

`world/common/downstream.py` 里判断写错了：

```python
if resp.status_code >= 500:        # ← 只把 5xx 当错误
    raise DownstreamFailed(...)
return resp.json()                  # ← 409 于是被当成成功返回
```

4xx 是"下游明确拒绝"，被当成了正常响应。

### 为什么它危险

**静默吞错比直接报错危险得多**：
- 上游据此报出成功状态
- 指标里 `5xx = 0`，看起来一切正常
- 排障时会被引向完全错误的方向

本次正是它掩盖了另一个问题（见下），让"故障注入不生效"这个假象持续了很久。

### 封堵措施

| 措施 | 说明 |
|---|---|
| 区分 `DownstreamRejected`（4xx）与 `DownstreamFailed`（5xx/超时） | 前者**不重试**（重试无意义），但**必须原样上抛** |
| 上游把 `DownstreamRejected` 映射为**同样的状态码与原因** | 不再伪造成功 |

### 回归用例

- `tests/test_offline.py::test_regression_4_downstream_4xx_is_rejected_not_success`
- `tests/test_offline.py::test_regression_4_4xx_must_not_retry`
- `tests/test_offline.py::test_regression_4_5xx_does_retry_then_fails`（对照）
- `tests/test_offline.py::test_regression_4_success_path_returns_payload`（正向对照，防"永远抛异常"的假绿）
- `tests/test_world.py::test_f2_does_exhaust_pool_and_show_503`（端到端：4xx 语义在真实链路上成立）

### 状态

- [x] 已修
- [x] 回归用例已落地
- [x] **已证明能变红** —— 做了变异测试：把 `400 <= code < 500` 改成永假（模拟旧缺陷），
      用例立刻报 `DID NOT RAISE DownstreamRejected`；还原后确认与提交版本逐字节一致

## #5　库存耗尽伪装成"故障注入失效"

**日期**：2026-09-24
**损失**：约 1 小时的排查时间

### 现象

六种故障逐个验证时，**五个场景的日志行数完全相同（7645）**，
且**所有场景 5xx 都是 0** —— 连 F2（池耗尽）、F5（风控报错）都不报错。

看起来像"故障注入根本没生效"。

### 根因（两个叠加）

1. **库存被压测抽干**：种子库存 1000/SKU × 3 = 3000 件，被前几轮压测（每轮 1500+ 请求）
   耗尽。库存一空，请求在 inventory 就被拒绝，**不再往下游走** ——
   于是 payment 收不到请求、日志断流、响应降到 15ms。
2. **#4 的静默吞错** 让这个失败完全不可见：409 被当成成功，5xx 计数为 0。

于是现象是"故障没生效"，真相是"请求走了另一条更短的路，而且那条路上的失败被吞了"。

### 封堵措施

| 措施 | 说明 |
|---|---|
| 种子库存提到 1,000,000 | 压测规模下不再耗尽 |
| 初始化改为**覆盖写**（去掉 `nx=True`） | 库存是**夹具数据**，重启后必须是确定值；否则打空之后重启仍是空的，场景无法复现 |
| 修掉 #4 的静默吞错 | 让此类失败**可见** |

### 回归用例

- `tests/test_world.py::test_regression_5_stock_is_not_drained`
  （断言：连续 60 个请求全部 2xx；库存精确扣减；跑完仍剩 >1000）
- `tests/test_world.py::test_injection_actually_takes_effect`
  （**元测试**：先证明注入真的改变行为，否则"F1 不失败"可能只是注入没生效的假绿）

### 状态

- [x] 已修
- [x] 回归用例已落地
- [x] **已证明能变红** —— 变异测试：把 `DEFAULT_STOCK` 从 100 万改回 1000，
      用例立刻报 `跑完 60 个请求后库存只剩 940 —— 种子值太小了`；
      还原后确认与提交版本逐字节一致

> **本条第 5 项修复（初始化改覆盖写）的可复现意义**：

## #6　日志解析漏掉整整一类行（占 21%，且含关键证据）

**日期**：2026-09-24（D3）
**损失**：无（开发期发现），但**会让降维结果不可信**

### 现象

降维报告显示：`未解析行数 6058（占 21.1%）`。

排查后发现被漏掉的是**第三方库写的日志**：

```
2026-09-24 04:59:22.064 INFO  HTTP Request: POST http://inventory:8000/reserve "HTTP/1.1 502 Bad Gateway"
```

这是 `httpx` 库自己的 logger 写的 —— 有时间和级别，但**既没有 `[service]` 段，
也没有 `trace=` 段**（它不是我们的 logger adapter 写的）。

### 根因

解析正则要求日志必须包含 `[service]`：

```python
r"\[(?P<service>[^\]]+)\]\s+"     # ← 写死了必填
```

于是这一整类行被判定为"无法解析"，只被计数，不进模板聚合。

### 为什么它危险

**这些行不是噪声，是证据。** `502 Bad Gateway` 正是"下游不可用"的直接观测。
如果降维把它们丢掉，Agent 就看不到那一层的失败 —— 而它恰好是判断
"故障发生在哪一层"的关键。

**更危险的是它很难被发现**：`未解析行数` 只是一个统计数字，如果不盯着看，
降维照常输出、报告照常漂亮，只是**悄悄少了 21% 的信息**。

### 封堵措施

| 措施 | 说明 |
|---|---|
| `[service]` 段改为**可选** | 三种变体（有 service+trace / 只有 service / 两者都无）都能解析 |
| 无 service 标记时回退到调用方传入的服务名 | 采集层是按服务分别读取日志的，所以能确定归属 |
| 保留"未解析行数"统计 | **它是这类问题的唯一暴露途径**，不许去掉 |

### 回归用例

- `tests/test_offline.py::test_regression_6_third_party_log_lines_are_parsed`
  （三种日志变体全都要能解析）
- `tests/test_offline.py::test_regression_6_unparsed_lines_are_counted_not_silently_dropped`
  （真正无法解析的行必须能被识别，而不是静默丢）

### 状态

- [x] 已修：未解析比例 **21.1% → 0.0%**
- [x] 回归用例已落地（9 条离线用例全绿）
- [x] **已证明能变红** —— 变异测试：把 `[service]` 段改回必填，
      用例立刻报 `这一行没能解析：'... HTTP Request: POST ... "HTTP/1.1 502 Bad Gateway"'`；
      还原后确认与提交版本逐字节一致

> **这条的元教训**：解析层**必须统计"自己没读懂多少"**。
> 一个只报告成功率的解析器，会把"读不懂"伪装成"不存在"。
> 本项目这条规则后来写进了 `reduce.py` 的设计：**未解析行数显式进 ReducedView**。

## #7　loadgen 超发 53%（数据量不可复现）

**日期**：2026-09-24（D2）
**损失**：无，但会让**需求假设 A1 的验收依据不成立**

### 现象

目标 1200 个请求，实际发出 **1841** 个（超 53%）。

### 根因

请求数上限**只在监控循环里检查**，而那个循环每 5 秒才醒一次：

```python
while not stop.is_set():
    await asyncio.sleep(5)          # ← 5 秒里可以发出几百个请求
    if total() >= max_requests:
        stop.set()
```

而有些场景（如 F2 池耗尽）跑得慢，5 秒只发几十个；有些场景跑得快，
5 秒能发上千个 —— **超发量随场景大幅波动**，于是"同样参数两次跑出不同数据量"。

### 为什么它危险

`单场景日志量 ≥3 万行` 是假设 A1 的验收标准。
如果请求数本身不可复现，**日志量也不可复现，这条验收就无法成立**。

### 封堵措施

请求数上限改为**由 worker 自己检查**（每次请求前看一眼），不再依赖监控循环：

```python
while not stop.is_set() and time.perf_counter() < deadline:
    if _total(stats) >= max_requests:
        stop.set()
        return
```

**理论上界**因此变为 `max_requests + concurrency`
（停止信号发出时，每个 worker 可能正在处理一个请求）。

### 回归用例

- `tests/test_world.py::test_loadgen_respects_max_requests`
  故意把监控循环调到 30 秒才醒一次 —— 若 worker 不自己检查，必然超发

### 状态

- [x] 已修
- [x] 回归用例已落地
- [x] 证明方式：用例把 `poll_s` 设成 30 秒，若停止只依赖监控循环则必然超出上界

## #8　F4「重试风暴」完全没效果（缺触发条件）

**日期**：2026-09-24（D2）
**损失**：无（在故障验证阶段发现）

### 现象

六种故障逐个验证时，F4 的结果与基线**一模一样**：

```
baseline   5xx=0   延迟 346.5ms
F4         5xx=0   延迟 346.5ms   ← 注入与不注入没有区别
```

### 根因

F4 的定义是"把 inventory 的重试次数从 1 改成 5"，**但重试只在调用失败时才发生**。
那一版没有让 payment 报错 —— payment 一切正常，所以重试永远不触发。

**重试次数从 1 改成 5，在"下游从来没失败"的前提下，和改成 100 没有区别。**

### 封堵措施

F4 必须**同时**具备两个条件：

| 条件 | 作用 |
|---|---|
| `payment.risk_error_rate = 0.6` | 制造失败（触发条件） |
| `inventory.downstream_retries = 5` | 放大失败（重试风暴） |

修完后实测：171 个 5xx、延迟 1622ms、日志 20,745 行（六种故障里最高）。

- `tests/test_world.py::test_f4_retry_storm_multiplies_downstream_traffic`
  断言：**每个请求平均引发的下游调用数 > 1.3**
  （若重试没被触发，这个值会接近 1.0）
