## ✅ D15 定稿数字（**两侧全部 7 个场景**，第一次可对等比较）

> D12 那一版的多 Agent 只跑了 **F1/F8 两个场景**，而 baseline 跑满 7 个 ——
> 所以"准确率相同"严格说只在两个场景上成立（当时也如实标注了）。
> D15 把 multi 补齐到**同样的 7 场景 × 3 轮**，于是两侧**样本对等**：

|                | baseline（7 场景 × 3 轮） | multi（**7 场景** × 3 轮） | 倍数  |
|----------------|---------------------------|---------------------------|-------|
| 样本           | 21 次尝试                 | **21 次尝试**             | —     |
| 准确率         | **100%**                  | **95.2%（20/21，按当前判据）**<br>存档判定为 90.5%（19/21）——判据后来修过，见 #48        | —     |
| 步数（LLM 轮次）| **8.3**                  | **28.8**                  | 3.5×  |
| 成本 / 次诊断  | **¥0.0172**               | **¥0.0732**               | **4.3×** |
| 收敛率 / JSON  | 100% / 100%               | 100% / 100%               | —     |

**结论变得更硬了**：在同样的场景、同样的样本数下，多 Agent
**多花 4.3 倍的钱、3.5 倍的时间，准确率却有降低**（方向明确，幅度见下）。
> 准确率按**当前判据**是 **95.2%**；存档当时那版判据给的是 90.5% —— 差别来自 #48（关键词匹配漏了英文词形）。两个口径都列在这里，见下面的说明。

> ⚠️ **幅度必须带上噪声带读（#46）**：那 9.5 个百分点**全部来自 F4 一个场景**
> （multi 1/3、baseline 3/3），而单场景每轮只有 3 次尝试 ——
> 3 轮的单场景准确率只能取 0/33/67/100，相邻两档差 **33 个百分点**。
> 同配置重跑的对照见下一节。

逐场景（multi）：

| F1 | F3 | **F4** | F5 | F6 | F7 | F8 |
|---|---|---|---|---|---|---|
| 100% | 100% | **33%** | 100% | 100% | 100% | 100% |

> ⚠️ **噪声带**：三轮的准确率是 86% → 100% → 86%（**每一轮都是一整个 7 场景的样本**），
> 也就是说"90.5%"这个数本身带着 ±7 个百分点的轮间波动 —— 必须连同噪声带一起读。
> 步数 27.7–29.6，成本 ¥0.0706–¥0.0748。

### 🔍 唯一的失败模式：F4（1/3），而且**不是尺子问题**

F4 =「重试风暴（配置漂移）」，方向**是反的**：症状在最下游 payment，
真根因在**上游** inventory（`W_INVENTORY_DOWNSTREAM_RETRIES: 1 → 5`）。
baseline 在 F4 上 3/3；multi 只在第 2 轮答对。

**两把尺子逐条对过（各判一次，成本合计 ¥0.0036）**：

| 轮 | 协调者做了什么 | 关键词 | 裁判 | 一致？ |
|---|---|---|---|---|
| 1 | 把配置漂移**降级**为放大器：「它本身不产生失败，只是放大」 | `absent` | `dismissed` | ✅ |
| 2 | 明确主张：「一条独立的、需要单独处置的脆弱点……不能仅作为伴随现象驳回」 | `asserted` | `asserted` | ✅ |
| 3 | **驳回**变更专员的主张，改把"stock_level ≈ 99.8 万"**提升为第二条根因** | `absent` | `absent` | ✅ |

第 3 轮那个"新根因"**不是异常**：`stock_level` 99.8 万是库存夹具的**正常余量**
（`DEFAULT_STOCK = 1_000_000`，见 ADR-0004 决定 5）；指标专员自己也说了
「我没有基线，无法判定是否真的偏离」，而协调者把它升级成了根因
—— **这是协调者制造的假阳性，它同时丢掉了真根因**。

> 📌 完整分析（含我一开始误判为"评分口径不对称"、以及怎么用实测否定它）见
> [`docs/harness-log.md`](harness-log.md) **#44**。

### 🎲 这个 9.5 个百分点**稳不稳**？—— 同一预算下的 2×2 对照（#46）

上面那个"低 9.5 个百分点"全部来自 F4。为判断它是真差距还是噪声，
我做了**同一预算**（都放宽到 `--max-steps 40`）的 2×2，每个格子 **3 轮**：

| F4 单场景 | baseline | multi |
|---|---|---|
| **flash @22**（上面那次主跑） | 3/3（100%） | **1/3（33%）** |
| **flash @40** | **2/3（67%）** | **2/3（67%）** |
| **v4-pro @40** | 3/3（100%） | 2/3（67%） |

**读法（很重要）**：

- **方向一致**：三次配对里 multi **一次都没超过** baseline（1/3 vs 3/3、2/3 vs 2/3、2/3 vs 3/3）；
- **幅度不可靠**：差距在 **0 ~ 67 个百分点**之间摆。
  最刺眼的一格是 **flash baseline 自己**：同配置、同场景，主跑 3/3、重跑 2/3 ——
  也就是说，**我引用的那 9.5 个百分点连"分母"自己都在抖**。
- ⇒ 能站住的结论是「**多 Agent 没有换来任何准确率优势**」，
  **不是**「低 9.5 个百分点」。措辞已在 README / 讲述稿 / 总览 / 页面里统一更正。

**顺带两个附带发现**：

1. **v4-pro 在本项目的预算下不匹配**：它在 `--max-steps 22` 下直接**撞上限不收敛**
   （1 次尝试：22 步、收敛 0/1、JSON 0%、准确率 0%），单次成本 ¥0.1707。
   放宽到 40 步才收敛。⇒ 换模型必须**重新校准预算**，否则量到的是配置差异（#13/#22 的同一课）。
   成本上：v4-pro baseline ¥0.1904/次、v4-pro multi ¥0.1924/次 —— 分别是 flash 同侧的
   **12.3 倍 / 2.6 倍**。
2. **运行器现在会自己喊**：单场景样本 ≤ 3 轮时，报告末尾会打印
   「单场景的差异只能看方向、不能比幅度」，并列出该样本量下的档位阶梯
   （见 `eval/runner.py::small_sample_warning`）。

## 二、这一对实验为什么是有效的（控制变量）

`(F1, F7)` 是本项目**唯一一处真正的控制变量对**：

| | 风控延迟 | 变更日志 | 物理事实 |
|---|---|---|---|
| **F1** | 800ms | **空** | 纯延迟，0 个 5xx |
| **F7** | 800ms | 有一条**无关**变更 | **与 F1 完全相同** |

两个场景的物理世界一模一样，唯一差别是**变更日志里多了一条"无关变更"**。
所以这一对能把「**抗不抗得住无关变更**」单独隔离出来 ——
而"抗不抗得住无关变更"正是多 Agent 交叉举证机制声称要解决的问题。

（F7 的真值经对照实验验证：只动红鲱鱼 → 122ms、0 个 5xx；只动真根因 → 905ms。
 详见 `docs/04-故障目录.md` 的 F7 小节。）

## 三、为什么 F7 **区分不出来**

看 baseline 在 F7 上的原始答案（三轮之一）：

> 外部风控依赖响应变慢（每次调用约 800ms），该延迟沿 payment→inventory→order
> 逐层向上传播，导致整条下单链路耗时升高（order 968ms / inventory 886ms /
> payment 812ms，其中风控占 801ms）。

**它根本没提那条变更。** 它从日志里直接读到"风控 801ms"，答完就结束了（4.3 步）。

所以 F7 虽然**有效**（真值可验证），但**太容易**：
正确答案在证据里太显眼，模型不需要与红鲱鱼搏斗就能拿到它。

→ 一个**可被轻易证伪**的红鲱鱼，区分不出任何能力。
→ 真正有区分力的红鲱鱼，必须"**有竞争力**"：看起来足够像，必须靠权衡证据才能否掉它。

**这一条本身是个发现**：红鲱鱼的难度不在"看起来像"，而在"**证据必须模棱两可**"。
而模棱两可的场景**很难构造** —— 它需要那条变更处在因果链上"几乎成立"的位置。
（F2 曾经做到过这一点，但代价是它**真的成立**了 —— 于是题目出反了。）

## 四、尚未验证的关键假设（下一步）

**目前所有场景都是"单故障"。**

三个专职 Agent 的价值本来应该体现在**信息量超出单个上下文/单条推理链**的时候：

- **多故障叠加**：同时注入两个互不相关的故障（例如 F1 的风控变慢 + F6 的内存泄漏）。
  单 Agent 可能只找到其中一个就收工；三个专职 Agent 各自只盯一路信号，
  反而可能各抓一个。
- **证据分散**：真根因的证据分散在三路数据源里，任一路都不足以单独定论。

`docs/05` 的"方法论限制"第 5 条早就写了这一点，但一直没有测。

> **在多故障场景被测过之前，"多 Agent 有没有用"这个问题没有完整答案。**
> 这也是接下来最该做的一件事（零改动成本：两个故障的补丁叠加即可）。

## 四、F8 多故障叠加：分工有效，但质证与裁决把第二个故障抹掉了

> ## 🔴 本节的数字来自**旧任务**（"定位根本原因"，单数）
>
> 改成"列出**所有**异常及其根因"并重跑之后，结论变了：
> **baseline 在 F8 上也拿到 3/3** —— 它把两个故障都找出来了。
> 所以"单 Agent 找不到第二个故障"这个现象是**任务定义造成的**，不是能力差异。
> 最终结论见 §一；下面保留旧口径的完整经过，
> 因为"**为什么会误判**"这件事本身比数字更有价值。

**F8 设计**（真值经对照实验验证，见 `docs/04`）：

| 故障 | 症状 | 证据在哪 |
|---|---|---|
| `payment.risk_latency_ms: 30 → 800` | 延迟（全链路 ~919ms） | payment 日志 + 风控指标（实测 801ms） |
| `order.leak_mb_per_req: 0 → 0.5` | 内存（实测 4.0 GiB） | **只在 order 的内存指标里，日志里没有** |

两者**因果完全独立**。正确的诊断必须**同时**给出两条。

**对照实验（零 LLM 成本）**：只泄漏 → 150ms / 764 MiB；只风控慢 → 905ms / 无泄漏；
叠加 → 919ms / 风控 801ms / 764 MiB。⇒ 两个故障的证据**完好共存、互不掩盖**。

### 实测结果

| | baseline | multi |
|---|---|---|
| **最终结论是否给出两个原因** | **0/3** | **0/3** |
| **过程中是否有人找到第二个故障** | **❌ 从未提及泄漏** | **✅ metrics 专员明确报出泄漏** |

**multi 三轮的完整经过**（三轮形状一致）：

1. **logs 专员** → 找到风控变慢（证据充分）
2. **metrics 专员** → 找到 order 内存泄漏 4.22e+09 字节（**这是 baseline 完全没做到的**）
3. **交叉质证** → metrics 专员**改口了**（`changed=True`）：
   「该泄漏在本窗口内未造成任何功能或资源影响……我原先的结论站不住脚」
4. **裁决** → 采纳 logs、**驳回 metrics**，把泄漏写成
   「**无功能/资源影响，是被放大的脆弱点而非触发者**」

⇒ **分工（信息隔离）确实起了作用：三路各盯一路，第二个故障被找到了。**
⇒ **但交叉质证 + 裁决把它降级掉了，最终结论与 baseline 一样不完整。**

### 两种读法，我不替读者选

F8 的判据是"只答出一个即为不完整"。而"答出"有两种解释。
**现在把它拆成了两个指标**（`eval/runner.py::attempt_cause_axes`，可从已有存档离线算出）：

| | 结论轴（最终答案有没有主张它） | 召回轴（任何环节有没有找到它） |
|---|---|---|
| **baseline** | 风控变慢 3/3 · 内存泄漏 **0/3** | 风控变慢 3/3 · 内存泄漏 **0/3** |
| **multi** | 风控变慢 3/3 · 内存泄漏 **0/3** | 风控变慢 3/3 · 内存泄漏 **3/3** |

⇒ **结论轴（同口径，可比较）：两边完全一样，都只给了一个原因。**
⇒ **召回轴（不同口径）：multi 覆盖到了第二个故障，baseline 从来没有。**
⇒ **multi 迄今唯一被验证过的优势，就是这个召回差异。**

⚠️ 召回轴**不是**同口径比较：multi 一轮有 7 个环节（3 调查 + 3 质证 + 1 裁决），
baseline 只有一个答案。它回答的是「**分工有没有覆盖到**」，不是「谁更强」。
报告里也照这句话打印了警告。

### ⚠️ 但这个判据有一个公平性问题，而且它比上面更根本

**当前的任务定义只问"根因"（单数）**：

```
TASK_PROMPT : "…请用工具收集证据，定位根本原因。"
输出契约     : "root_cause": "一句话说清根本原因"     ← 单数
工作原则 2   : 区分"症状"与"根因"                    ← 单数
```

所以在 F8 上判"漏了第二个故障"= **拿一个它没被交付的任务去考它**。

而且 metrics 专员的改口**不是无理取闹**：泄漏在本窗口内确实没有可观测影响
（0 错误、全部成功、池空闲），"它不是**本次延迟**的触发者"这句话**是对的**。

⇒ **要公平地测"多故障"这个能力，必须先把任务改成**
「**列出本时段所有异常及其根因**」—— 而且**对两边同时改**。

**代价（必须说清）**：这要改 `baseline.py` 的 prompt，
而 `baseline.py` 有**内容指纹**守着（D6 立的规矩）——
改动会让指纹用例变红，纪律要求：① 更新指纹；② **重跑 baseline 并更新 `docs/05`**。
也就是说：**现有全部数字会再次作废一次**。

⇒ 所以这一步**不能顺手做**，它是一个独立的、需要重新基线化的单元。
计划与成本见 `docs/00-状态.md` §二。

## 五、代价（无论结论如何都要记）

> 下面两小节（三、五）是**旧任务口径**下的观测。最终口径见 §一。

| 项 | baseline | multi | 倍数 |
|---|---|---|---|
| 步数（LLM 轮次，旧任务） | 4.3 – 5.0 | 27.0 – 29.0 | **~6×** |
| 成本 / 次（旧任务） | ¥0.0088 – ¥0.0091 | ¥0.0576 – ¥0.0672 | **6.3 – 7.6×** |
| 步数（新任务） | 7.5 → **8.3** | **26.5**（未重跑） | — |
| 成本 / 次（新任务） | ¥0.0165 → **¥0.0172** | **¥0.0674**（未重跑） | — |
| JSON 解析成功率（新任务） | 67% → **100%**（#27 催促） | **100%** | — |

> 多 Agent 的"贵"是**结构性的**，不是调优问题：
> 3 次调查 + 3 次质证 + 1 次裁决 = 7 次调用起步，
> 而 baseline 一次问答只要 7–8 轮（新任务）。
>
> 有意思的是：**新任务让 baseline 变贵了**（¥0.0120 → ¥0.0165，步数 6.2 → 7.5），
> 于是多 Agent 的相对成本从 6× 降到 **4.1×**。
> （baseline 那一侧后来又因 JSON 催促涨到 ¥0.0172 / 8.3 步 → **约 3.9×**；
>   但 multi 未同步重跑，所以这一格的精确倍数**暂不下结论**。）
> **这不是多 Agent 变便宜了，而是 baseline 的任务变难了** ——
> 两个版本的倍数**不可直接比较**，这一点必须写清楚。

## 六、方法论限制（必须连同数字一起读）

1. **准确率在有效场景上已经饱和**（两边都 100%）——
   天花板效应让"更好"无法体现。要区分能力，需要**更难的题**，而不是更多的轮次。
2. **样本量小**：每格 3 次。
3. **只测了 `deepseek-flash`**，没测 `v4-pro`。
4. **F2 已作废**（harness-log #20），F4 判据过窄 ——
   本项目目前的"有效场景"实际只有 6 个（F1/F3/F4*/F5/F6/F7）。
5. **多故障场景未测**（见第四节）—— 这是最大的一个缺口。
6. 评分仍是**关键词组 + 否定语境判定**，不是 LLM 裁判（D10 的内容）。

## 七、这件事对项目意味着什么

**结论是负的，但这个负结果比一个假的正结果有价值得多** ——
因为它是**在把测量修对之后**才得到的：

- D5 的 83.3% 是**评分口径错误**（把"被否掉的提及"算作命中）；
- F2 的 0% 是**题目答案反了**；
- 多 Agent 的"100%"曾是**同一个评分缺陷**造成的假成功。

一条条修完之后，剩下的就是真相：**在这个世界里，一个单 Agent 已经够用了。**

> 项目最初的命题是「LLM 的『自觉』不可靠 —— 要用确定性的工程机制约束它的判断和行动」。
> **这个命题没有被推翻** —— 但它现在的证据来自**测量侧**（#11–#20 那十条），
> 而不是来自"多 Agent 比单 Agent 准"。
>
> 如果最终结论就是"多 Agent 在这个实验里没有增量"，
> 那也是**一个诚实、可复现、可被面试官亲手验证的工程结论** ——
> 而且它比"我做了个多 Agent 系统，准确率提升了 X%"要值钱得多。
