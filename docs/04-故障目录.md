# 04 · 故障目录（D2 设计）

> ## 这份文档的唯一职责
>
> **定义六种故障：怎么注入、症状在哪、根因在哪、期望看到什么遥测、标准答案是什么。**
>
> 它是评测集的地基——`eval/scenarios/` 里的每个场景都由这里的一个故障（或组合）构成。
> 标准答案从这里取，**不在别处重复**。

---

## 一、设计准则

### 准则 1：症状位置 ≠ 根因位置（必须跨服务）

这是需求假设 **A3** 的实现手段。

**为什么这条是生死线**：如果症状和根因在同一处，单 Agent 一句话就能定位，
"多 Agent"就是装饰品。只有让症状与根因**分离**，多视角交叉验证才有真实价值。

→ **六种里五种跨服务，一种同源（作为对照组）。**

### 准则 2：注入不碰代码

全部通过环境变量注入。**改配置即注入，不用改代码，不用重建镜像。**

### 准则 3：症状必须"看起来像别的毛病"

朴素诊断必须会得出**错误**结论。否则这道题没有区分度。

### 准则 4：必须有对照组

第 6 条故意让症状与根因同源。**用它诚实地报告"多 Agent 什么时候不管用"**——
这比只报喜的评测可信得多。

## 三、逐个详解

### F1｜外部依赖变慢

**注入**：`W_PAYMENT_RISK_LATENCY_MS=800`（正常值 30）

**传播路径**
```
external risk control 变慢 800ms
      ↓
payment  扣款耗时 800ms
      ↓
inventory 等待并透传耗时
      ↓
order    下单耗时 800ms+
```

**期望遥测**

| 服务 | 日志 | 指标 |
|---|---|---|
| order | `下单成功 ... 耗时=8xxms` | `handler_duration_ms` 上升 |
| inventory | `库存预留成功 ... 耗时=8xxms` | `handler_duration_ms` 上升 |
| payment | `外部风控响应缓慢 耗时=8xxms` ★ | `risk_control_duration_ms` 上升 |

**朴素诊断会怎么错**
- 只看 order → "order 变慢了，查 order"
- 只看 metrics → 三个服务的 `handler_duration_ms` **全都涨了**，看不出谁先谁后
- **必须沿 trace 下钻到 payment**，才能看到 `风控耗时=800ms` 这条唯一的根因证据

**标准答案**：payment 的外部风控依赖延迟升高（≥800ms）

---

### F2｜连接池耗尽（放大效应）★ 最有价值

> ## 🔴 2026-09-24 重大修正：**本场景声明的标准答案是反的**（harness-log #20）
>
> 用对照实验（`scripts/exp_pool_vs_latency.py`，零 LLM 成本）实测：
>
> | 格 | pool_limit | risk_latency_ms | **HTTP 5xx** |
> |---|---|---|---|
> | 基线 | 64 | 30（正常） | 0 |
> | F1 | 64 | 800 | **0** |
> | **只动池** | **2** | **30（正常）** | **851（56%）** |
> | F2 | 2 | 800 | 1487（97%） |
>
> **池改小单独就足以造成事故**（下游完全健康时也有 851 个 5xx）；
> 风控变慢只是把失败率从 56% 抬到 97%。
>
> 用 but-for 判据：去掉池改小 → 事故消失；去掉风控变慢 → 事故仍在。
> ⇒ **池被改小才是事故的根因，风控变慢是放大器。**
> ⇒ 下面写的"标准答案"**与实测相反**，**必须重设**（见 harness-log #20）。
>
> 另外下面那句"把池调大只会把崩溃推迟"**被实测否定**：
> 池保持 64、风控同样 800ms 时，**5xx = 0**，不是推迟，是根本不发生。
>
> ⚠️ 本节正文**保留不改**，因为它是"当时是怎么想的"的记录 ——
> 而"当初为什么会定反"这件事本身，比正确答案更有教学价值。

**注入**：`W_PAYMENT_RISK_LATENCY_MS=800` + **变更** `W_ORDER_POOL_SIZE=2`（原值 8）

**传播路径**
```
payment 变慢
      ↓
order 的请求开始堆积（每个都揣着一个连接在等下游）
      ↓
order 连接池被抽干（池大小 2，在途 2）
      ↓
后续请求：连接池获取超时 → 503
```

**期望遥测**

| 服务 | 日志 / 指标 |
|---|---|
| order | WARNING `连接池等待 350ms（池大小=2，当前在途=2）`<br>→ ERROR `连接池获取超时：等待 2000ms 后放弃`<br>→ `requests_total{result="pool_exhausted"}` 上升 |
| payment | `外部风控响应缓慢 耗时=8xxms` |
| 变更日志 | `order.POOL_SIZE: 8 → 2` ← **红鲱鱼** |

**朴素诊断会怎么错** ← 这个场景的全部价值所在
- 最显眼、最"像根因"的信号是 order 的池耗尽 → 得出 **「把 order 的池调大」**
- 而且**变更日志还在旁边帮倒忙**：确实有一条"池大小被改小"的记录
- 但这个结论是**错的**：把池调大只会把崩溃推迟，根因在 payment

**交叉举证应该这样工作**
- 日志 Agent → H1「order 连接池容量不足」
- 指标 Agent → H2「payment 的外部风控耗时飙升」
- 变更 Agent → C1「order 池大小在故障前被改小」（**会加强 H1，是干扰项**）
- **Coordinator 必须驳回 H1**：要求它给出一条能证伪 H2 的证据。
  H1 给不出——因为"池太小"解释不了"为什么 payment 的风控耗时同时飙升"。
  → 判定 H2 为根因，order 池耗尽是被放大的**症状**。

**标准答案**：外部风控延迟升高；order 池耗尽是其被放大的后果，不是根因

> ⚠️ **这是全项目最能体现核心命题的场景**：
> 单 Agent 很可能给出"调大连接池"这个看似合理、实际错误的结论。
> 多 Agent 的交叉举证机制才能挡住它。

### F3｜本环节数据访问变慢

**需要代码钩子**：`W_INVENTORY_SLOW_OP_MS`（在 inventory 的数据访问处加一个可控延迟）

**注入**：`W_INVENTORY_SLOW_OP_MS=600`

**传播路径**：inventory 自己慢 → order 等它

**期望遥测**

| 服务 | 日志 |
|---|---|
| order | `下单成功 ... 耗时=6xxms` |
| inventory | `库存预留成功 ... 耗时=6xxms`，**但它的下游调用很快** |
| payment | `扣款成功 ... 总耗时=31ms` ← **正常** |

**朴素诊断会怎么错**
- F1 和 F3 的 order 侧症状**一模一样**（都是"order 变慢"）
- 区分点是**耗时断层在哪一层**：
  - F1：inventory(8xx) ≈ payment(8xx) → 问题在更下游
  - F3：inventory(6xx) **但** payment(31ms 正常) → 问题就在 inventory
- **单看 order 的日志，这两者无法区分。**

**标准答案**：inventory 的数据访问变慢

---

### F4｜重试风暴（配置漂移）★ 方向相反

**注入**：变更 `W_INVENTORY_DOWNSTREAM_RETRIES`：1 → 5

**传播路径**
```
inventory 每次调用 payment 失败后重试 5 次
      ↓
payment 收到的请求量放大 5 倍
      ↓
payment CPU 升高、线程/连接紧张
```

**期望遥测**

| 服务 | 日志 / 指标 |
|---|---|
| inventory | WARNING `调用下游 payment 第 1/5 次失败` … `第 5/5 次失败` |
| payment | `requests_total` **暴涨**（同一 order_id 出现多次） |
| 变更日志 | `inventory.DOWNSTREAM_RETRIES: 1 → 5` ← **真根因** |

**朴素诊断会怎么错**
- 症状在 payment（QPS 暴涨）→ 很容易得出 **「payment 被打爆了，需要扩容」**
- **方向完全反了**：问题是上游在重复打它，扩容只会更贵地重复同样的错误

**标准答案**：inventory 的重试次数被从 1 改为 5（配置漂移）

> ## ⚠️ 2026-09-24 补充：本场景的判据**过窄**（harness-log #20 的同类检查）
>
> 用对照实验实测（零 LLM 成本）：
>
> | 格 | downstream_retries | risk_error_rate | 结果 |
> |---|---|---|---|
> | 只动重试 | **5** | 0（正常） | **0 个 5xx，什么也没发生**（重试只在失败时才触发） |
> | 只动错误率 | 1（正常） | **0.5** | **= F5，764 个 5xx** |
> | 都动（= F4） | 5 | 0.5 | payment QPS 暴涨 + 171 个 5xx |
>
> ⇒ 两个变量**各自是不同侧面的必要因**：
> 错误率是"请求失败"的必要因，重试次数是"payment QPS 暴涨"的必要因。
>
> ⇒ 所以"重试次数是根因"**站得住**（它是本场景特征症状的必要因），
> 但"外部风控错误率是触发者、重试只是放大"**也站得住** ——
> 而现在的判据（必须命中"重试"+"inventory"）会把后者判错。
>
> **结论：本节不是反的，是窄的。** 判据应放宽到接受两类表述，
> 或把标准答案改得更精确：
> 「payment 的 QPS 暴涨源于 inventory 的重试配置漂移（5 次），错误率是触发条件」。

> 这个场景与 F1/F2/F3/F5 方向相反——用来打破"往上游找就对了"的定式。

### F5｜外部依赖报错
**注入**：`W_PAYMENT_RISK_ERROR_RATE=0.5`

**期望遥测**

| 服务 | 日志 |
|---|---|
| payment | `外部风控调用失败（模拟）耗时=30ms` + `扣款失败` |
| inventory | `调用下游 payment 第 1/1 次失败` + `库存预留失败（下游不可用）` |
| order | `下单失败（下游不可用）` + 502 |

**与 F1 的区别**：F1 是**慢**，F5 是**错**。
- F1：耗时飙升，成功率不变
- F5：耗时正常（30ms），错误率飙升

**标准答案**：外部风控的错误率升高

### F6｜内存泄漏（对照组）

**需要代码钩子**：`W_ORDER_LEAK_MB_PER_REQ`（每次请求往一个只增不减的字典里塞数据）

**注入**：`W_ORDER_LEAK_MB_PER_REQ=2`

**期望遥测**：order 进程内存持续上升；最终变慢或崩溃

**这一条是刻意设计的对照组**

症状与根因**同源**（都在 order），单 Agent 一句话就能定位。
**在评测报告里要如实写明：这一类故障多 Agent 没有优势。**

> 报告"多 Agent 什么时候不管用"，比只报喜可信得多。

---

### F7｜无关变更干扰（合格的红鲱鱼）★ 承担 F2 原本的职责

> ## 为什么会有这个场景
>
> F2 原本承担"红鲱鱼"职责，但**对照实验证明它出反了**：
> 那条被当作红鲱鱼的变更（池 64→2）**就是真根因**，
> 于是它把答对的扣分、把答错的加分（harness-log #20）。
>
> F7 是重做的版本。它的定义性判据是：
> **那条被记录的变更，必须在因果上与事故无关** ——
> 而且这一点不能靠声明，必须能被实验证明。

**真根因（不写进变更日志）**：`W_PAYMENT_RISK_LATENCY_MS: 30 → 800`

**红鲱鱼（写进变更日志）**：`W_ORDER_POOL_ACQUIRE_TIMEOUT_MS: 2000 → 1200`

**为什么那条变更在因果上无关**

因为它**从来不会被触及**：

```
负载并发 50  ⇒ order 侧最多 50 个请求同时在途 ⇒ 最多占 50 个连接
池容量 64    ⇒ 池永远不满 ⇒ 没有任何请求等待过连接
             ⇒ "获取连接的等待上限"这个参数**根本没有被读过**
```

**为什么它又像一个根因**

因为它长得太像了 —— "有人在故障前一分钟把连接池的等待上限从 2000ms 砍到 1200ms"。
只看变更日志的人会立刻得出"**超时被调小，导致请求失败**"。

**而数据能证伪它（这正是本场景要考的能力）**

| 证据 | 期望值 |
|---|---|
| `pool_in_flight` 峰值 | < 64（池从没满过） |
| `pool_exhausted` 计数 | **0** |
| "连接池等待" WARNING | **0 条** |
| **HTTP 5xx** | **0** —— 那条变更预言的是"请求失败"，而一个失败都没有 |

**标准答案**：payment 的外部风控延迟升高；order 的池获取超时被调小是**无关变更**
（从未被触及：池从未满、零等待、零池耗尽、零 5xx）

#### F7 的真值验证（★ 第一个被对照实验验证过的场景）

按 harness-log #20 立下的规矩：**一道题如果说不清"谁移除后事故消失"，它就不该有标准答案。**
所以 F7 在写进目录之前先做了控制变量实验（`scripts/exp_pool_vs_latency.py`，零 LLM 成本）：

| 臂 | 施加了什么 | 平均延迟 | 池耗尽 | HTTP 5xx | 判定 |
|---|---|---|---|---|---|
| 臂1 | **只动红鲱鱼**（超时 1200） | 122ms | 0 | **0** | 红鲱鱼单独**什么都没做** ✓ |
| 臂2 | **只动真根因**（风控 800ms） | **905ms** | 0 | 0 | 真根因单独**复现了症状** ✓ |
| 臂3 | 两个都动（= F7 本身） | ≈ 臂2 | 0 | 0 | — |

臂2 的旁证：`risk_control` 实测平均 **800.9ms**（`sum/count = 1.2246e6/1529`），
与注入的 800ms 吻合 —— 证明**指标确实反映的是这件事**，不是别的。

⇒ **but-for 判据成立**：去掉真根因 → 延迟回到 122ms；去掉红鲱鱼 → 症状不变。
⇒ **真根因是风控延迟；那条被记录的变更是无关的。** 这正是 F2 声称要做、却没做到的事。

---

#### F7 与 F1 构成一对严格对照 ★

F7 的物理条件与 **F1 完全相同**（都只有"风控变慢"这一件事），
唯一差别是 **F7 的变更日志里多了一条无关变更**。

| 场景 | 风控 | 变更日志 | 预期答案 |
|---|---|---|---|
| **F1** | 800ms | **空** | 风控变慢 |
| **F7** | 800ms | 有一条**无关**变更 | 风控变慢（且要能说明那条变更为什么无关） |

所以 (F1, F7) 这一对能把「**是不是被无关变更带偏了**」单独隔离出来 ——
而"抗不抗得住无关变更"恰恰是多 Agent 交叉举证机制声称要解决的问题。

> **这是整个评测里唯一一处真正的控制变量对。**
> 它回答的问题是："多 Agent 的交叉举证，到底有没有用？"
> —— 而不是"多 Agent 整体准不准"（那个数字被六个场景的混合难度糊住了）。

⚠️ **前提是被强制的，不是靠提醒的**：并发必须 < 池容量（64）。
见 `scripts/inject_fault.py::_check_f7_precondition` ——
不满足时**拒绝执行**，而不是打印一条警告然后照跑（`harness-log #1` 的教训：靠人记得必然失效）。

## 四、第三路信号：变更事件日志

Agent 的三个信息源是「日志 / 指标 / 变更」。前两者由服务产生，
**第三路必须由故障注入器产生**。

**格式**：一行一个 JSON，写入 `runs/<run_id>/changes.ndjson`

```json
{"ts":"2026-09-24T10:12:03+08:00","target":"order","key":"W_ORDER_POOL_SIZE","from":"8","to":"2","by":"injector"}
```

**关键设计**：变更日志同时承载**真信号**和**红鲱鱼**。

| 场景 | 变更日志内容 | 性质 |
|---|---|---|
| F2 | `order.POOL_SIZE: 8 → 2` | **红鲱鱼**（真根因在 payment 的风控延迟，而那不是一条"变更"） |
| F4 | `inventory.DOWNSTREAM_RETRIES: 1 → 5` | **真信号** |

所以**变更 Agent 不能"看到变更就说是它"**——它必须和其他两路交叉验证。

> 这正是需求 FR-1.3「信息隔离」的价值：每一路都有盲区，谁都单独定不了根因。

## 五、数据量要求（假设 A1）

**目的**：让单 Agent 无法把原始遥测一次读完，从而必须做摘要——
而摘要恰好会丢掉关键信号（例如"15 分钟前有一次配置变更"这种低熵高价值信息）。

| 项 | 目标 |
|---|---|
| 单场景日志行数 | **≥3 万行**（目标区间 3–8 万） |
| 跨服务 | 三个服务的日志都要有量 |
| 时间窗 | 30 分钟 |
| 产生方式 | `world/loadgen/` 持续打流量 |

**待确认**：数据量靠"高并发短时"还是"中并发长时"堆出来？
