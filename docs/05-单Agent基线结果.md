## 四、唯一的失败模式：掉进"红鲱鱼"陷阱（F2）

三轮的结论原文：

```
第1轮 ❌ "order 服务的连接池大小在 05:44:18 被从 64 改为 2，
        池容量骤降导致连接池瞬间饱和，1483 个下单请求在等待 400ms 后失败。"

第2轮 ❌ "order 服务的连接池大小被从 64 误改为 2（05:44:18 的配置变更），
        导致连接池瞬间耗尽，绝大多数下单请求在等待 400ms 后失败。"

第3轮 ❌ "order 服务的连接池大小 W_ORDER_POOL_SIZE 被从 64 误改为 2，
        导致 order 自身连接池容量骤降、在途请求瞬间占满…"
```

**三轮一次都没有提到外部风控。**

### 为什么这是最有价值的一条发现

这三个答案**看起来非常专业**：

- 它们**引用了变更记录**，还带上了准确的时间戳（05:44:18）
- 它们**解释了症状**（1483 次请求 400ms 超时失败）
- 它们给出的**机制是自洽的**（池从 64 变 2 → 容量骤降 → 耗尽）

**唯一的问题是：它们错了。**

F2 的真根因是 **payment 的外部风控响应从 30ms 劣化到 800ms** ——
它让每个请求占用连接约 1 秒，才是把池耗尽的直接原因。
而**这条劣化根本不在变更记录里**（外部依赖变慢不是一次"配置变更"），
只能从**指标**里看出来。

> **agent 手上是有这份证据的。** 它调用了 `query_metrics`（13 次工具调用里包含），
> 但它**停在了变更记录给出的那个"看起来完整的故事"上**。

### 与"步数预算"的相互作用（一个反直觉的观察）

| 预算 | F2 准确率 | 平均步数 |
|---|---|---|
| `max_steps=8` | **67%** | 5–6 |
| `max_steps=14` | **0%** | **4–5** |

**预算变大之后，它反而用更少的步数、给出更浅的答案。**

把两次实验的 6 次尝试合起来看：**4 次掉进陷阱，2 次答对。**

> 样本量太小，不足以断言"预算与准确率负相关"。
> 但它足以说明：**F2 是这个 baseline 的稳定弱点，不是偶发失误。**

## 五、对 D6/D7 的含义

baseline 给出了一个**非常干净、非常集中的靶子**：

| # | 靶子 | 当前值 | 多 Agent 的对应机制 |
|---|---|---|---|
| **1** | **归因错误（红鲱鱼）** | **F2 = 0%** | **Coordinator 强制交叉举证**：假设必须提供能**证伪其他假设**的证据 |
| 2 | 工具调用偏多（F3 达 45 次） | 平均 23 次 | 职责分工后每个 Agent 的工具面更小 |
| 3 | JSON 解析成功率 83% | 18 次里 3 次未产出结构化结论 | 职责更窄 ⇒ 输出契约更简单 |
| 4 | 成本 | ¥0.0120 / 次 | 模型路由：便宜模型整理证据、强模型做归因 |

### 一句必须说清楚的话

> **baseline 已经很强了（83.3%，五个场景满分）。**
>
> 所以多 Agent 的价值**不可能来自"整体更准"** ——
> 它只有一个明确的位置：**F2 这类"证据齐全但归因错误"的场景**。
>
> **如果多 Agent 修不好 F2，那它就不值得这份复杂度。**
> 这个结论也必须如实报告 —— 一个诚实的"多 Agent 在这个任务上不划算"，
> 比一个编出来的提升数字有价值得多。

## 六、方法论的诚实声明（限制）

1. **评分用关键词组，不是 LLM 裁判。**
   确定、零成本、可审计，但**死板**：措辞不同但意思正确的答案可能被判错。
   例：F2 第 1 轮的答案里若加上一句"其中外部风控耗时 800ms 是触发因素"，
   就会被判对 —— 而它和判错的版本在**结论质量上差别不大**。
   → D10 会加入 LLM 裁判并做人工校准。

2. **样本量小。** 3 轮 × 6 场景 = 18 次。F2 更是只有 3 次（合并两次实验为 6 次）。
   → 调参阶段需要更多轮次。

3. **场景数据量只有 5000–9000 行**，远低于需求的 3–8 万行。
   这对 baseline **有利**（上下文压力更小）。
   → **当前数字应视为 baseline 的上界。**

4. **只测了 `deepseek-flash`。** 换 `deepseek-v4-pro` 大概率更准，
   但成本和延迟都要重新测。**没有测，就不下结论。**

5. **六个场景都是"单故障"。** 真实生产里常见的是多故障叠加，
   那才是对多 Agent 更有利的场景，但**本项目没有测**。

---

## 七、一句话结论

> **单 Agent baseline：准确率 83.3%，六轮噪声带 83%–83%，收敛率 100%。**
>
> **六个场景里五个满分，唯一稳定失败的是 F2（红鲱鱼陷阱），0/3。**
>
> 它失败的方式不是"没找到证据"，而是**停在了一个自洽的、引用了变更记录的、
> 看起来很专业的错误结论上** —— 而这正是 Coordinator 的交叉举证机制
> 被设计出来要解决的问题。
