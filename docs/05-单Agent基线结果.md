## 四、失败模式分析（**本节是本文档最有价值的部分**）

### 模式 1：掉进"红鲱鱼"陷阱（F2，33%）

F2 的设计意图是：**最显眼的信号（order 池耗尽）+ 变更日志里一条真实变更（池大小 64→2）
合起来构成一个看起来完全合理的错误结论**。正确根因在 payment 的外部风控。

三轮里两轮掉进去了，原文实录：

```
第1轮 ❌ "order 服务的连接池大小被从 64 改为 2（配置变更
        order.W_ORDER_POOL_SIZE: 64→2），池容量过小，在下游链路单次请求
        耗时约 1.1s（其中外部风控占 801ms）的情况下连接被长时间占用，
        池瞬间耗尽，导致大量下单请求等待 400ms 后失败。"

第2轮 ❌ "order 服务的连接池大小被从 64 改为 2（配置变更
        order.W_ORDER_POOL_SIZE: 64→2），导致连接池被瞬间耗尽，
        下单请求大面积失败。"

第3轮 ✅
```

**值得注意**：第 1 轮**其实提到了外部风控 801ms**，但仍然把根因归给了池大小 —— 它
看到了全部证据，却没有把"外部依赖劣化"排到第一位。这是**证据齐全但归因错误**，
比"没看到证据"更难修。

> ⚠️ **重要发现：单轮冒烟测试时它答对了。**
> 我第一次只跑 1 轮，得到 100%，差点得出"baseline 不掉陷阱"的结论。
> **跑 3 轮才看到真实分布。这就是噪声带的全部意义。**

### 模式 2：被"响亮信号"吸走，漏掉"安静信号"（F6，33%）

F6 是我设计的**对照组** —— 我原本预期"症状与根因同源 ⇒ 单 Agent 也容易答对"。

**结果它是并列最差的，只有 33%。**

```
第1轮 ✅
第2轮 ❌ 结论为空（撞上步数上限）
第3轮 ❌ "payment 调用的外部风控（risk_control）依赖发生故障，
          导致扣款失败并逐层向上游传播为 inventory/order 的下游失败。"
```

第 3 轮是**纯粹的幻觉** —— 它编了一个 payment 的问题，而 F6 的故障在 order 自身。

**为什么它反而最差**：F6 的信号是 `leak_bytes` 这个**安静的指标**（数值上升，
没有任何 ERROR 日志）。而其他场景里都有大量 ERROR/WARNING 在"喊"。
Agent 被响亮的信号吸走了。

> **这推翻了我的一个假设**：同源故障 ≠ 容易定位。
> 真正的区分点不是"症状与根因的距离"，而是**信号有多响亮**。

### 模式 3：不收敛 / 不产出结论（18 次里 5 次）

- **收敛率 89%**：2 次撞上 8 轮上限就停了
- **JSON 解析成功率 72%**：5 次没产出可解析结论

**这是独立于准确率的第二个问题**：baseline 不是"答错"，而是**"没答"**。

从 `fully_converged_rate` 与 `json_parse_rate` 的差（89% vs 72%）可以看出：
有 3 次虽然收敛了，但给的是**自由文本而非 JSON 结论**，无法被自动判定。

工具调用次数也偏高（平均 24 次，F3 达到 34 次）—— 说明它在**反复取相同的数据**，
缺少"我已经掌握够了"的判断。

## 五、对 D6/D7 的含义：多 Agent 必须解决什么

baseline 给出了**四个具体、可量化的靶子**。多 Agent 设计只有命中其中至少一个，才算有价值：

| # | 靶子 | 当前值 | 多 Agent 的对应机制 |
|---|---|---|---|
| 1 | **归因错误（红鲱鱼）** | F2 = 33% | Coordinator 强制交叉举证：假设必须能证伪其他假设 |
| 2 | **漏掉安静信号** | F6 = 33% | 信息隔离：每个 Agent 只看一路，避免被别处的噪声吸走 |
| 3 | **不收敛 / 不产出结论** | 收敛 89% / JSON 72% | 结构化输出 + 更窄的职责 |
| 4 | **工具调用低效** | 平均 24 次 | 职责分工后每个 Agent 的工具面更小 |

**另外还有成本这一维**：baseline 全部用同一个模型。
多 Agent 可以用便宜模型做证据整理、强模型做归因推理（模型路由）。

## 六、方法论的诚实声明（限制）

1. **评分用关键词组，不是 LLM 裁判。**
   确定、零成本、可审计，但**死板**：措辞不同但意思正确的答案可能被判错。
   例：F1 第 2 轮结论为空导致判错（那其实是"没答"而非"答错"）。
   → D10 会加入 LLM 裁判作为补充，并做人工校准。

2. **样本量小。** 3 轮 × 6 场景 = 18 次。噪声带（33%–83%）说明这个量级
   **只够看出"不稳定"这个事实，不够给出精确的中心值**。
   → 调参阶段需要更多轮次。

3. **场景是统一的 30 并发 / 1500 请求**，与真实生产的负载形态不同。
   数据量偏小（约 5000–9000 行），远低于需求里说的 3–8 万行。
   → 这对 baseline **有利**（上下文压力更小）。若跑到 3 万行，
   它的表现可能更差。**当前数字应视为 baseline 的上界。**

4. **`deepseek-flash` 是便宜模型。** 换 `deepseek-v4-pro` 大概率更准，
   但成本和延迟都要重新测。**没有测，就不下结论。**

---

## 七、一句话结论

> **单 Agent baseline：准确率 61.1%，但轮间波动 33%–83%。
> 它在"红鲱鱼"场景上只有 33%，在"安静信号"场景上也只有 33%，
> 且 18 次里有 5 次根本没产出可判定的结论。**
>
> 这个基准线**足够低、且有明确的结构性失败模式**，
> 因此多 Agent 有真实的改进空间 —— 前提是它必须命中第五节列出的靶子之一。
