## 二、下一步（确切的、可执行的任务）

### 🔴 当前最重要的事：验证最后一个假设 —— **多故障叠加**

**先说已经确认的结论**（完整数据见 **`docs/06-多Agent结果.md`**）：

| 场景 | baseline | multi | 成本倍数 |
|---|---|---|---|
| **F1**（无红鲱鱼） | **3/3** | **3/3** | 6.3× |
| **F7**（有红鲱鱼） | **3/3** | **3/3** | 7.6× |

⇒ **在现有场景上，多 Agent 没有可证明的价值增量，代价 6–8 倍。**
⇒ F7 的红鲱鱼**有效但太容易**（baseline 根本没提那条变更，直接从日志答完）。

### 为什么还不能就此收尾

**目前所有场景都是"单故障"。** 而三个专职 Agent 的价值本该体现在
**信息量超出单个上下文 / 单条推理链**的时候 —— 也就是**多故障叠加**。

`docs/05` 的"方法论限制"第 5 条早就写了这一点，但一直没有测。
**在它被验证之前，只能说"现有证据不支持多 Agent"，不能说"多 Agent 没用"。**

### 具体怎么做（改动成本接近零）

1. **新增多故障场景**：把两个互不相关的故障的补丁叠加即可。
   首选 **F1（风控变慢）+ F6（内存泄漏）**：
   - 一个跨服务（payment）、一个同源（order）
   - 一路体现在日志/下游延迟、一路体现在内存指标
   - 两者因果上完全独立 —— 单 Agent 很可能只抓到其中一个就收工
2. **对照实验先行**（零 LLM 成本）：用 `scripts/exp_pool_vs_latency.py`
   验证两个故障叠加后**各自的证据都还在**（否则又是一个"题目出错了"）。
   ⚠️ 这是 harness-log #20 立下的规矩：**没有对照实验，就不许写标准答案。**
3. **跑 (baseline, multi) × 3 轮**（约 ¥0.25）：
   - 若 baseline 只找到其中一个、multi 两个都找到 ⇒ **多 Agent 的价值第一次被证明**
   - 若两边都找到 ⇒ 结论收敛为"多 Agent 在这个世界里没有增量"，如实写进报告

### 几条不要忘的（都是已经付过代价的教训）

**降维规则（机制保证，不靠调参）**

```
ERROR / WARNING 模板  →  无条件全部保留（哪怕只出现 1 次）
INFO 模板             →  按频次保留前 12 个
```
朴素做法"取出现次数最多的 N 条"会漏掉**只出现一次的关键 ERROR**。

**本阶段新发现的缺陷**（详见 `docs/harness-log.md`）

| # | 缺陷 | 影响 |
|---|---|---|
| **#6** | 解析正则要求必须有 `[service]`，导致第三方库（httpx）写的日志**整类被漏掉** | 占全部日志 **21%**，且含关键证据（"下游 502"）；修复后 **21.1% → 0.0%** |

**一条重要观察（影响评测设计）**

> **严重故障会减少遥测产量。**
> F2（池耗尽）只产出 3,900 行，而 F5（错误率）产出 28,728 行。
> 原因：池耗尽让 97% 的请求**在到达下游之前就失败了**，系统根本没干活。
>
> 所以「单场景 ≥3 万行」这条验收标准**不能对所有故障一视同仁** ——
> 对"系统崩溃类"故障，数据量天然更少。这是真实的运维现象，如实记录。

> 详见下方"评分口径修正"与 `docs/harness-log.md` #16。
> 旧口径的数字保留在此，是为了让"结论变了多少、为什么变"可追溯。

| 指标 | 值（旧口径） | 轮间噪声带 |
|---|---|---|
| **① 准确率** | **83.3%** → **修正后 61.1%** | **83% – 83%** |
| **② 步数** | 6.2 轮 LLM / 约 23 次工具调用 | 5.5 – 6.5 |
| **③ 成本** | **¥0.0120 / 次诊断** | ¥0.0108 – ¥0.0128 |

各轮：**83% → 83% → 83%**（旧口径，完全稳定）　｜　收敛率 **100%**　｜　JSON 解析成功率 **83%**

> ⚠️ **这份数字作废过三次**，详见 `docs/05` §零 与 harness-log #12 #13 #16：
> 1. 第 1 版 61.1% —— **指标未被场景窗口化**，Agent 读到的是历史累计值
> 2. 第 2 版 77.8% —— **`max_steps=8` 是随手定的**，恰好卡在 F3 需要的最少步数之下
> 3. 第 3 版 83.3% —— **评分把"被否掉的提及"算作命中**，两条答反的答案被判对
>    （修正后 **61.1%**，与第 1 版数字巧合相同，但**原因完全不同**：第 1 版是读脏数据，
>    这一版是评分口径）
>
> 三次都不是"算错了"，而是**测的不是我以为的那个东西**。
> 这也说明：**"准确率"这个数字本身，比它的两次作废记录更值得怀疑。**

**逐场景：六个里四个满分（新口径）**

| ID | 场景 | 旧口径 | **新口径** |
|---|---|---|---|
| F1 | 外部依赖变慢 | 3/3 | **3/3** |
| **F2** | **连接池耗尽（红鲱鱼陷阱）** | 0/3 | **0/3** |
| F3 | 本环节处理变慢 | 3/3 | **3/3** |
| **F4** | **重试风暴（配置漂移）** | 3/3 | **1/3** ⚠️ |
| F5 | 外部依赖报错 | 2/3 | **2/3** |
| F6 | 内存泄漏（对照组） | 3/3 | **3/3** |
| | **合计** | 15/18 | **11/18 = 61.1%** |

> **修正的性质**：不是"分数变了"，而是**两条本来就答反的答案被旧评分判对了**。
> F4 的标准答案是"inventory 的重试次数 1→5（配置漂移）"，
> 而 baseline 答的是"外部风控不可用…inventory 的重试次数变更**只是**放大了错误量，**并非根因**"。
> 旧口径因为这两个词都出现过而给了分。
> **结论：旧口径的 baseline 83.3% 是高估的。**

**两个失败模式（新口径下）**

| # | 场景 | 失败方式 |
|---|---|---|
| 1 | **F2（0/3）** | 停在自洽的**红鲱鱼**结论上（引用了变更记录、时间戳、机制自洽，但没把外部风控当根因） |
| 2 | **F4（1/3）** | 同样"答反"：**知道**重试次数变了，却把它降级成"只是放大了错误量" |

> **两条是同一个失败模式**：**提到了真根因，但把它判成了非根因。**
> 而这恰好是 D7 交叉举证机制**应该**挡住的那类错误。

**这对 D6/D7 是一个极其干净的靶子**

| # | 靶子 | 当前值 |

### D6 已完成 ✅ —— 三个专职 Agent（信息隔离）

**核心不是"三个 Agent 更聪明"，而是"每个 Agent 客观上存在盲区"。**

理由：如果每个 Agent 都能看到全部数据，"多 Agent"就只是**同一份数据问三遍**——
成本三倍、信息零增益。只有让每个角色的结论都是**不完整的**，协作才产生真实价值。

**交付物**

| 文件 | 职责 |
|---|---|
| `src/rca/agents/roles.py` | LOGS / METRICS / CHANGE 三角色定义 + 各自的 `system_prompt` + `OUTPUT_CONTRACT` |
| `src/rca/agents/specialist.py` | `SpecialistAgent`、`investigate_all(parallel=True)`、`Hypothesis` |
| `src/rca/tools.py` | `RestrictedToolBox` —— **隔离不是靠 prompt 写"你只能看日志"，是靠工具面真的只开一个** |
| `scripts/run_specialists.py` | 单角色可独立运行（用于观察"盲区"是否真实存在） |

**结构上的保证**

- 每个专职 Agent 拿到的是 `RestrictedToolBox`，**只挂载自己那一个工具**；
  越权调用会被拒绝并计入 `denied_tool_calls`（该值应当恒为 0）。
- `OUTPUT_CONTRACT` 强制要求填 `needs_from_others` ——
  **每个 Agent 必须显式说出"我还缺什么信息"**，这是"盲区真实存在"的可观测证据，
  也是第二轮交叉质证的问题来源。

**回归用例**：`tests/test_agents.py` 18 条（边界真的存在，而不只是 prompt 里写了）。

### D7 🚧 进行中 —— Coordinator 与交叉举证

**设计上的三个决定**（理由写在 `src/rca/agents/coordinator.py` 头部）

| # | 决定 | 为什么 |
|---|---|---|
| 1 | 第二轮**只给"结论"，不给"原始数据"** | 给了原始数据，隔离就白做了；不给，才逼出**对抗性**（要用自己的数据去证伪别人） |
| 2 | 第二轮**允许再次调工具** | 给回查机会。F2 里 LogsAgent 自己的日志中**确实有**"外部风控响应缓慢 耗时=800ms"，第一轮没注意、第二轮可能被逼出来 |

### ⚠️ 三条踩过的坑（同一个编码机制，已造成 4 次不同后果）

1. **可执行脚本必须纯 ASCII**（`.ps1` / `.bat` / `.cmd` / `Makefile`）。
   PowerShell 5.1 会把 UTF-8 无 BOM 的脚本按 GBK 读，
   中文被 mangle 后**会破坏语法**。见 `docs/harness-log.md` #1 #2。
2. **中文路径下不要用 PowerShell 读写文本文件**，用 `read`/`write`/`edit` 工具。
   （顺带：`Get-Content` 读 UTF-8 文件时连**行号都是错的**，别用它定位行。）
3. **Python 脚本要打印非 ASCII，必须给 stdout 兜底**：

   ```python
   try:
       sys.stdout.reconfigure(encoding="utf-8", errors="replace")
   except Exception:
       pass
   ```

   stdout 接到**管道/文件**时会退回本地编码 GBK，打印 emoji 直接抛
   `UnicodeEncodeError`，**整段输出和退出码一起丢掉**。
   `encoding` 和 `errors` **缺一不可**（只加 `errors` 不崩了，但输出仍是 GBK 字节、全是乱码）。
   实测对照表见 `AGENTS.md` 第 4 条"坑 4"；自动检查见 `test_regression_p4_*`。

## 七、更新纪律

**每完成一个里程碑，必须：**

1. 更新本文件的「一、当前进度」与「二、下一步」
2. 如有新决策 → 写一条 `docs/adr/`

**为什么这么严**：上下文会随对话变长而失真，但**文件不会**。
