### 1.2 LLM：DeepSeek（以下均为实测核实结论）

**当前合法模型名只有两个**（旧的 `deepseek-chat` / `deepseek-reasoner` 已于 2026-07-24 停服，**不是别名**）：

| 模型 | 用途 | 并发 |
|---|---|---|
| `deepseek-flash` | 日志解析、摘要、工具选择 | 2500 |
| `deepseek-v4-pro` | 根因推理、冲突裁决 | 500 |

BASE URL：`https://api.deepseek.com`（OpenAI 兼容）

#### ⚡ 三个坑 —— D0 spike 实测结论（2026-09-24）

> ⚠️ 本节已由实测数据修订。原先基于二手资料的第 2 条**已被证伪**。

| # | 坑 | 实测结论 | 处理 |
|---|---|---|---|
| 1 | **`thinking` 默认 `enabled` 且真计费** | 让它答"收到"两字即产生 `reasoning_tokens=13`；带工具的两轮对话中推理 token 占输出 **15%–26%** | 关闭方式**只能**用 `extra_body={"thinking":{"type":"disabled"}}`。⚠️ `enable_thinking=False` **静默失效**；`thinking=False` 报 422 |
| 2 | ~~带 `tools` 的多轮必须回传 `reasoning_content`，否则 400~~ | ❌ **未复现，判为不成立**。四种组合（第2轮 thinking 开关 × 是否回传）在 `deepseek-flash` + OpenAI 兼容端点 + 两轮工具调用下**全部成功** | 仍保留该字段，但理由是**成本核算与调试可见性**，非接口强制 |
| 3 | 缓存字段 | **有两套**：DeepSeek 的 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`，以及 OpenAI 标准的 `prompt_tokens_details.cached_tokens`。缓存**自动**生效，实测第 2 轮即出现命中（`cache_hit=128`） | 两套都读，据此算真实命中率 |

**坑 2 的未覆盖范围**（若日后在这些场景遇到 400，优先怀疑它）：`deepseek-v4-pro`、3 轮以上、Anthropic 兼容端点 `/anthropic`。

> **这条修订本身是 spike 的价值所在**：spike 的作用不是确认已知风险，而是把它证伪——
> 我们因此不必为一个**不存在的约束**去设计消息适配层。

#### 成本（已核实）

| 计费项（每百万 token） | 空闲时段 | 高峰时段 |
|---|---|---|
| 输入（缓存**命中**） | ¥0.02 | ¥0.04 |
| 输入（缓存**未命中**） | ¥1 | ¥2 |
| 输出 | ¥4 | ¥8 |

（flash 价格；v4-pro 约 4.5 倍）

- **高峰时段仅为工作日 9:00–12:00、14:00–18:00**；晚间、周末、法定节假日全天都是空闲时段 → **本排期几乎 100% 落在半价区**
- 缓存命中与未命中**差 50 倍** → prompt caching 是成本第一杠杆，且要求工具 schema 保持稳定前缀
- 粗估：**单场景约 ¥0.2**，12 场景一轮 < ¥3 → **成本不是约束**，可放心做大量重复实验

### 1.3 LangGraph 1.2.12 要点（已核对 wheel 源码）

- `Send` 的正确导入：**`langgraph.types`**（`langgraph.constants` 已废弃）——网上多数教程仍是旧路径
- `create_react_agent` **已废弃**（这是 1.x 的主要变更）
- `durability` 默认 `"async"`，不是 `"sync"`
- 「检查点器有统一 `Checkpointer` 协议」**不成立**——它只是类型别名 `None|bool|BaseCheckpointSaver`
- `astream_events` 的 `version="v1"` 至今仍是默认（"v1 被移除"的说法与官方 release notes 矛盾）

### 1.4 MCP Python SDK 2.2.0（v2 重写了客户端 API）

- **只剩一个 `Client`**；`ClientSession` 降级为 `client.session` 逃生舱——`ClientSession` + `stdio_client` + `initialize()` 那套三层写法**已非推荐路径**
- `FastMCP` → **`MCPServer`**
- wire 属性从 camelCase 改为 **snake_case**
- `transport` 配置移到 `run()`
- 依赖由 `httpx` 换成 **`httpx2`**（TLS 走系统信任库）

### 1.5 存储

| 用途 | 选型 |
|---|---|
| Agent 状态 / checkpoint | SQLite |
| 遥测（日志/指标/变更） | 文件（NDJSON）+ SQLite 索引 |
| trace / 审计 / 成本 | SQLite |
| 被诊断系统依赖 | Redis（仅缓存击穿场景需要），不引 Postgres |
| **向量库** | **不引入**（见 §四 不做清单） |

## 二、架构

```
┌── Agent 侧（Python）────────────────────────────────┐
│  Coordinator（supervisor + 强制交叉举证）             │
│    ├─ LogsAgent      工具面：仅 query_logs           │
│    ├─ MetricsAgent   工具面：仅 query_metrics        │
│    └─ ChangeAgent    工具面：仅 get_deploys          │
│  上下文压缩 · progress 断点续跑 · Loop 四层防御       │
└────────────────┬───────────────────────────────────┘
                 │ ① MCP（工具面收口，无旁路）
┌── 策略执行点（独立进程）★ ──────────────────────────┐
│  路径规范化 → 白名单前缀比对                          │
│  动词分级矩阵（read<write<delete<move-outside<force）│
│  不可逆操作默认拒绝 + 显式授权（带 TTL）              │
│  ★ 隔离区：不存在硬删除（删除 = 移入隔离区 + TTL）    │
│  拒绝也记账（审计不可静默丢失）                       │
└────────────────┬───────────────────────────────────┘
                 │ ② 只读遥测
┌── 遥测层（Python）─────────────────────────────────┐
│  接入 → ★降维（原始 3–8 万行 → 几千 token）         │
└────────────────┬───────────────────────────────────┘
                 │
┌── 被诊断世界（自建、开源、可注入）──────────────────┐
│  order → inventory → payment（FastAPI × 3 + Redis） │
│  chaos：6 种故障注入（Agent 不可见）                 │
│  loadgen：流量生成                                  │
└────────────────────────────────────────────────────┘
```

### 三个关键架构决策

| 决策 | 选择 | 理由 |
|---|---|---|
| **策略执行点独立进程** | 是 | 让"边界不受 Agent 侧影响"成为**结构性事实**，而不是纪律（FR-2.9） |
| **遥测降维在 Agent 之外** | 是 | 原始遥测永不进上下文；一石三鸟：成本主杠杆 + 上下文工程考点 + 保护信噪比 |
| **不存在硬删除** | 隔离区 + TTL | 事故无法挽回的根因不是"守卫没拦住"，而是**物理层面没留退路**（FR-2.6） |

## 三、评测设计（本项目的深水区）

### 3.1 场景划分

| 集合 | 数量 | 用途 |
|---|---|---|
| **调优集** | 8 | 调试 prompt、工具、路由，可反复跑 |
| **留出集** | 4 | **调试期物理隔离**（`holdout/` 目录在 D12 之前不读取），只用于最终评测 |
| 真实事故 | 3 | 本案 + `fulearn` 真实故障史，单独报告 |
| **合计** | **15** | |

### 3.2 故障设计（A3 原则：症状位置 ≠ 根因位置）

依赖链：`order → inventory → payment`

| # | 故障 | 症状位置 | 根因位置 | 跨边界 |
|---|---|---|---|---|
| 1 | 连接池耗尽（payment 池配置过小） | order 响应慢、CPU 升 | payment 配置 | ✅ |
| 2 | 慢查询（inventory 缺索引） | order 超时 | inventory DB | ✅ |
| 3 | 下游超时（payment 调外部风控变慢） | order 错误率升 | payment 依赖 | ✅ |
| 4 | 缓存击穿（Redis key 过期风暴） | inventory QPS 飙 | inventory 缓存策略 | ✅ |
| 5 | 配置漂移（inventory 重试次数被改大） | payment 被打爆 | inventory 配置 | ✅ |
| 6 | 内存泄漏（order 中间件泄漏） | order GC/OOM | **order 自身** | ❌ **对照组** |

> **第 6 条是刻意设计的对照组。** 它用来诚实地说明：**多 Agent 的优势不是普遍的**——当症状与根因同源时，单 Agent 同样能定位。
> **把这个结论写进报告，比只报喜的评测可信得多。**

### 3.3 指标

| 指标 | 定义 |
|---|---|
| 定位准确率 | 根因判对的比例（含噪声带，重复 3 轮） |
| 平均排查步数 | 工具调用 + 推理轮次 |
| 单次成本 | token × 单价，含缓存命中率 |
| **分子报告** | 单 Agent / 多 Agent 各自在 6 类故障上的表现 |

### 3.4 执行顺序（不可颠倒）

```
D5  先做单 Agent baseline  → 拿到三个数字
D10 再做多 Agent 评测       → 才有"提升"可谈
```

> 顺序反了，数字就是编的。
