# rca-agent

> **LLM 的「自觉」不可靠 —— 所以用确定性的工程机制，同时约束它的判断和它的行动。**

一个**可复现**的多 Agent 故障根因分析（RCA）实验：
它诊断一个自建的三服务系统，并把**"测量本身可信"**当成第一目标 ——
包括诚实地报告一个**否定自己的结论**。

> 📌 **想直接看结论**：`demo/rca-demo.html`（双击打开，无需服务器）。
> 那个页面由存档生成、可逐字节重放，**不花一分钱就能核对本文里的每个数字**。
>
> 📌 **进度 / 计数 / 封堵状态**一律看 [`docs/00-状态.md`](docs/00-状态.md) ——
> 那是唯一权威，本文不复制。

## 一、最重要的结论是**负结果**

> **多 Agent 没有可测的价值增量。**

同一个世界、同一套评分、同一个计价时段、同样的步数上限：

| | 单 Agent（baseline） | 多 Agent（三专员 + 交叉质证 + 裁决） |
|---|---|---|
| 准确率 | **100%**（7 场景 × 3 轮） | **100%**（F1/F8 × 3 轮） |
| 步数（LLM 轮次） | **8.3** | **28.7**（3.5×） |
| 成本 / 次诊断 | **¥0.0172** | **¥0.0690**（4.0×） |

多花 4 倍的钱、3.5 倍的时间，**准确率一点没变**。

**但比这个结论更重要的是：它是被测量出来的，而一路上我七次得到过相反的结论。**
每一次"多 Agent 有效"的发现，最后都发现是**尺子坏了**（评分把被否定的提及算作命中、
场景的标准答案是反的、任务定义从没要求"找全"、计价模型漏了法定节假日……）。
这七次翻案逐条记在 `demo/rca-demo.html` 第四节和 [`docs/harness-log.md`](docs/harness-log.md) 里。

## 二、核心命题：约束"判断"和"行动"

| | 不可靠的"自觉" | 本项目用的确定性机制 |
|---|---|---|
| **判断面** | 单视角确认偏误：先看到 CPU 飙升，就一路去找流量证据 | **信息隔离**（三个专员各自只看自己那一路遥测）+ **强制交叉举证**（假设必须引用 `evidence_id`，机械校验）—— 已实现 |
| **行动面** | 模型"自己会小心" | **默认拒绝**：按角色限定工具面 + 路径规范化 / 动词分级 / 隔离区 / 审计（`src/rca/policy/`）—— 机制已实现且有 27 条用例，**接到 Agent 路径这件事尚未完成**（见第三节） |

**把软约束做成硬约束**：交叉质证不是提示词里的一句话，而是协议层的检查 ——
假设没引用证据直接被驳回；引用的证据全在支持自己、没有一条能证伪他人，也要被驳回。

```
        │   coordinator.py（交叉质证 + 裁决）                     │

        ┌─────────────────┴────────────────────────────────────┐
        │  工具面：3 个**只读**工具                              │
        │   query_logs / query_metrics / get_changes            │
        │   角色隔离：RestrictedToolBox ← 已实现且有用例          │
        └──────────────────────────────────────────────────────┘
                          │  只读遥测（原始遥测永不进入上下文）
        ┌─────────────────┴────────────────────────────────────┐
        │  遥测：接入 → 降维（压缩到 0.217%，信号全存活）          │
        └──────────────────────────────────────────────────────┘
                          │
        ┌─────────────────┴────────────────────────────────────┐
        │  被诊断世界：order → inventory → payment → 外部风控     │
        │  自建 FastAPI，8 种可注入故障，Redis，一条命令起全栈     │
        └──────────────────────────────────────────────────────┘
```

**已实现**（每条都能指到文件/用例）：

| 能力 | 在哪 |
|---|---|
| 三个 FastAPI 服务 + Redis，可注入 8 种故障 | `world/`、`scripts/inject_fault.py`、[`docs/04-故障目录.md`](docs/04-故障目录.md) |
| 遥测接入与降维（原始遥测不进上下文） | `src/rca/telemetry/` |
| 角色隔离的工具面（3 个只读工具） | `src/rca/tools.py`（`RestrictedToolBox`） |
| 单 Agent 与多 Agent 两条诊断路径 | `src/rca/agents/baseline.py`、`specialist.py`、`coordinator.py` |
| 评测 harness（关键词主判 + LLM 裁判交叉校验、噪声带、存档、轨迹） | `eval/runner.py`、`eval/judge.py` |
| 策略执行点（路径守卫 / 动词分级 / 隔离区 / 审计） | `src/rca/policy/`（27 条用例；**尚未接到 Agent 路径**，见下） |
| **错误封堵清单**：一条错误只有在**回归用例能变红**之后才算封堵 | [`docs/harness-log.md`](docs/harness-log.md) + `scripts/mutate_check.py` |

**未接线**（写在 README 里就必须说清，见 `docs/harness-log.md` #41）：

| 没有的东西 | 现状 | 这意味着什么 |
|---|---|---|
| **LangGraph** —— **未接线** | 依赖里有，代码里**一次都没用**（编排是手写循环） | 如果你要看"state graph / checkpointer"，这里没有 |
| **MCP 收口** —— **未接线** | 依赖里有，代码里**零行 MCP**；工具是进程内直调 | 工具面**没有经过 MCP 收口**，因此**"无旁路保证"尚未成立**（FR-2.1 未完成） |
| **策略执行点接到 Agent 路径** —— **未接线** | `src/rca/policy/` 已实现且有 27 条用例，**但只被测试 import** | 边界机制是**建好了、还没接上**；目前工具面只有只读工具，所以还没有"不可逆操作"需要它拦 |
| **断点续跑** —— **未实现** | 未做（AC-10 未验证） | 进程被杀就得重跑 |

> 这一栏是刻意留在首页的。一个把"没做的部分"写在首页的项目，
> 比一个只在角落里标一句"未接线"的项目可信得多 —— 而**可信**是这个仓库要证明的唯一一件事。

## 四、自己核对（**零成本**，不需要 API key）

```bash
git clone <repo-url> && cd rca-agent
uv sync                                  # 依赖锁定在 uv.lock
```

然后（Windows 下用 `.\.venv\Scripts\python.exe` 代替 `uv run python`）：

| 想核对什么 | 命令 | 预期 |
|---|---|---|
| **页面确实由存档生成** | `uv run python scripts/make_demo.py` | `git status` **依然干净** —— 重放逐字节一致 |
| **文档里的成本构成** | `uv run python scripts/cost_breakdown.py runs/_recordings/record-deepseek-flash.ndjson --list` | 文件里有 3 次运行；`--run 1` 得到命中率 79.5% / 输出 72.3% |
| **全部回归用例** | `uv run pytest` | 全绿（数字见 `docs/00-状态.md`） |
| **封堵是不是空的** | `uv run python scripts/seal_report.py` | 每条"已封堵"都有变异组背书，退出码 0 |

> ⚠️ 跑 pytest 时**不要再加 `-q`**：`pyproject.toml` 的 `addopts` 里已经有 `-q`，
> 再加一个会变成 `-qq`，pytest 会把结果行一起吞掉。

**要花钱的部分**（真跑评测）：需要 `DEEPSEEK_API_KEY`、需要起被测世界（Docker + Redis），
两侧合计约 **¥0.8**。命令形如：

```bash
uv run python eval/runner.py --agent baseline --rounds 3              # 单 Agent，7 个场景
uv run python eval/runner.py --agent multi --faults F1,F8 --rounds 3  # 多 Agent，2 个场景
```

`--mode replay` 可以完全从录制回放、**不调 API**（未命中会直接报错，不会悄悄花钱）；
但仓库里提交的是 `record-*.ndjson`（用于成本分解的 3 次运行），
**不是一份完整的 `replay-*.ndjson`** —— 所以"零成本重放整套评测"目前**还不成立**。

## 六、诚实边界（数字要连同这些一起读）

- 多 Agent 只在 **F1（无干扰对照）与 F8（多故障）** 两个场景上测过；其余五个**未测**，不能外推
- 每侧只有 **3 轮**；只测了 `deepseek-flash`，**未测** `deepseek-v4-pro`
- 被诊断系统是**自建**的：故障是**注入**的，不是自然发生的；"根因"由我定义的判据裁定
- 评分主判据是**关键词/判据式**判定，LLM 裁判只做**独立交叉校验**（不参与正确性计算）
- 一条错误只有在**回归用例能变红**之后才算封堵；标记为"靠人"的流程缺陷**没有**自动化证明
- 这里的"安全"是**机制**，不是**保证**：任何守卫都可能被绕过
